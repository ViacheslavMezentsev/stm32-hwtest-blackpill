он пока не содержит проверяемого контракта HAL/CMSIS. Identity проверяется до

один непрерывный Flash-образ. Расширение совместимости сначала проектируется,
затем реализуется и проверяется — будущие поля нельзя молча добавить в текущую схему.

## Базовая периферия F411/F103

Базовые блоки уже включены в IOC обоих профилей. Таблица описывает их назначение;
результаты перечислены выше. CRC и Stop остаются отдельными будущими опытами.

| Блок | Настройка первого опыта | Что сможем проверять |
| --- | --- | --- |
| SYS/GPIO | SWD, LED output: F411 PC13, F103 PB2 | Подключение, регистры, базовый цикл, восстановление после опыта |
| ADC1 | Temperature Sensor + VREFINT, 12 bit, right alignment, scan из 2 рангов, software trigger, continuous off | Порядок каналов, raw-коды, преобразования, ошибки/timeout |
| DMA для ADC1 | Peripheral → memory, halfword/halfword, memory increment, normal mode, IRQ | Два элемента буфера, завершение, callback, владение буфером, повторный старт |
| TIM2 | Internal clock, update IRQ, период около 100 мс, без выходных пинов | IRQ, счётчик событий, freeze при halt, позднее запуск ADC от таймера |
| RTC | LSI, Alarm interrupt; время/счётчик и повторная постановка alarm в ПО | События, backup domain, пробуждение, обработка pending flags |
| PWR | Sleep/WFI уже используется; Stop — следующий отдельный опыт | Возврат из сна, источник пробуждения, восстановление clock tree |
| CRC | Включить аппаратный CRC | Проверка известных векторов, reset/accumulate, порядок байтов |

Для ADC выбрать rank 1 = Temperature Sensor, rank 2 = VREFINT. Максимальное время
выборки для начала: F411 — 480 cycles, F103 — 239.5 cycles; ADC clock выбрать
заведомо ниже предела из datasheet. После генерации проверим фактическую частоту,
время установления внутренних каналов и порядок включения. У F103 добавить
калибровку ADC перед первым стартом в прикладной инициализации.
Scan из двух каналов сначала читаем через DMA, а не двумя произвольными чтениями DR:
нужно гарантировать, что первое преобразование не потеряно до чтения второго.

TIM2 пока не использовать как триггер ADC: сначала отдельно подтвердим software
sequence/DMA и timer IRQ. Потом добавим синхронизацию через поддерживаемый данным
ADC источник TRGO/CC; одинаковое название таймера не гарантирует одинаковую маршрутизацию.

В CubeMX включить соответствующие NVIC interrupts (DMA, TIM2, RTC alarm).
Конкретный DMA channel/stream выбирается по MCU через CubeMX, а не копированием F411.
Начать с HSI и LSI, чтобы не зависеть от наличия/качества внешних кварцев;
при изменении IOC повторно сверять тактовые частоты и делители.

## ADC: температура и питание

ADC измеряет отношение входа к VREF+/VDDA. Чтение VREFINT позволяет оценить VDDA;
это не переключение всего ADC на внутренний источник опорного напряжения.
Встроенный датчик измеряет температуру кристалла, а не точную температуру воздуха.

F411 имеет заводские данные калибровки температуры и VREFINT; использовать их
по документации конкретного MCU, с компенсацией питания. У F103C8 не предполагаем
аналогичную таблицу F4: оценка по типовым параметрам заметно грубее и требует
индивидуальной калибровки для точных значений. Пределы теста должны учитывать
допуски источника/датчика, а не сравнивать с одним «идеальным» числом.
[F411 datasheet](https://www.st.com/resource/en/datasheet/stm32f411ce.pdf),
[F103x8/xB datasheet](https://www.st.com/resource/en/datasheet/stm32f103tb.pdf).

Первые проверки: raw не равен 0/полной шкале, DMA записал оба ранга, последовательные
измерения обновляются, VDDA физически правдоподобна. Это проверки работоспособности;
точность VDDA подтверждается мультиметром, температура — отдельным эталоном и методикой.
Изменение результатов при нагреве не заменяет калибровку абсолютной температуры.

## RTC и PWR: различия профилей

F411 имеет календарный RTC, alarm и wakeup timer; у F103 старый RTC со счётчиком,
second/alarm событиями, без аналогичного wakeup timer F4. Первый общий сценарий —
alarm, следующая ступень F411 — отдельный wakeup timer. С LSI проверяем факт событий
и разумный диапазон, не точность секунд. LSE добавим после проверки кварца платы.
[F411 datasheet](https://www.st.com/resource/en/datasheet/stm32f411ce.pdf),
[F103x8/xB datasheet](https://www.st.com/resource/en/datasheet/stm32f103tb.pdf).

Порядок: Sleep → Stop → Standby. Текущий Sleep намеренно сохраняет SysTick для
периодического пробуждения. Для опыта с пробуждением только от RTC нужна отдельная
политика SysTick; после Stop — явное восстановление необходимого тактирования.
Для Standby нужен отдельный тест загрузки после пробуждения, поскольку состояние
обычной RAM теряется. Использовать backup/reset flags и документировать reset policy.
Текущий reset/run раннера не равен сбросу backup domain: состояние RTC не обязательно
исчезнет между тестами. Будущий сценарий должен явно выбрать, сохранять или очищать его.

Проверки под подключённым SWD и настройки DBGMCU могут менять поведение сна.
Различаем функциональную проверку входа/выхода и измерение потребления без влияния
отладчика. Ток платы с LED/стабилизатором/ST-Link не равен току самого MCU.
Standby и watchdog пока не включать в автоматически запускаемую при старте цепочку.

## Дальнейшее расширение

- EXTI: сначала программное возбуждение для маршрута IRQ; затем внешний фронт
  для проверки пина и фильтрации. Это разные доказательства.
- USART + DMA: сначала контракт и передача, затем loopback/приём, framing/overrun.
  Потребуется соединение или второй узел; UART/VCOM сейчас не подключаем.
- SPI: full-duplex loopback MOSI–MISO, режимы/размеры/порядок, затем внешний slave.
- I2C: внешний slave для реальной передачи/ACK; без него можно проверить NACK/timeout.
- IWDG/WWDG: отдельная прошивочная конфигурация/сценарий reset с учётом debug freeze;
  не включать IWDG постоянно до подготовки recovery и проверки подключения NRST.

## Почему одного IOC и -g3 недостаточно

IOC создаёт конфигурацию и код init. DMA start, постановку alarm, вход в сон,
обработку результатов и повторный запуск обычно должен делать прикладной код.
Именно небольшой автономный сценарий «периодическое измерение → обработка → сон»
сделает ELF полезным объектом проверки без встраивания тестового раннера в MCU.

`-g3` добавляет debug info и макросы; он не отключает оптимизацию и не удерживает
неиспользуемые функции. При `--gc-sections` даже собранная HAL-функция может исчезнуть
из ELF. Проверять наличие символов через nm/GDB после линковки.
[GCC: Debugging Options](https://gcc.gnu.org/onlinedocs/gcc/Debugging-Options.html).

Для специального опыта можно явно удержать нужные функции через `--undefined`/`KEEP`,
но это отдельный вариант сборки и другой объект доказательства. Предпочтительный
первый вариант — реальные вызовы нужных возможностей из штатного приложения.
[GNU ld: options](https://sourceware.org/binutils/docs/ld/Options.html).

Отсутствие HAL-функции в ELF не делает регистры MCU недоступными через SWD: можно
обратиться по адресам из RM. Это уже сценарий управления аппаратурой отладчиком,
а не проверка того, что приложение правильно использует периферию. Для MMIO нужно
учитывать побочные эффекты, доступность тактирования и зависимость от конкретного MCU.


## Будущий профиль h503cb: порядок ввода

Владелец уточнил маркировку: **STM32H503CBT6**, IOC выбирает STM32H503CBTx.
Генерация задаёт 128 KiB Flash и 32 KiB RAM. Получены Core/startup/linker и SVD;
CubeMX 6.18.0 / CubeH5 V1.7.0. [Аудит и инструкция CubeMX](H503_CUBEMX.md).
Pinout LED, кварцы и питание подтвердить отдельно: название BlackPill их не гарантирует.

1. MCU и IOC получены; закончить настройку DMA/IRQ/RTC, сверить pinout и согласовать замену BluePill.
2. Выбрать и закрепить CubeH5/HAL/CMSIS, MCU define, startup/linker и SVD.
   В полученном IOC выбран CubeH5 V1.7.0; закрепить эту версию в сборочном профиле.
   Сначала отдельная сборка h503cb без аппаратного запуска.
3. Проверить backend/версию сервера и прошивку отладчика. В текущем OpenOCD 0.12.0
   файл target для H5 не обнаружен. Проверить подходящий OpenOCD либо ST GDB Server;
   последний потребует реального backend-адаптера, текущий раннер поддерживает OpenOCD.
4. До записи Flash проверить identity, размер/карту памяти, vector/reset, доступ
   к SRAM/MMIO и аппаратным breakpoint. Состояние доступа к отладке читать отдельно;
   штатные тесты не должны менять product state, option bytes или OTP.
5. Подключить минимальные GPIO/RCC/SysTick, затем последовательные ступени ниже.
   Для каждой ступени фиксировать положительный сценарий, отказный случай и влияние halt.

### Особенности и периферийные ступени H503

По [DS14053](https://www.st.com/resource/en/datasheet/stm32h503eb.pdf), H503 использует
Cortex-M33, GPDMA, 12-битный ADC, RTC, LPTIM, DAC, компаратор/OPAMP, I3C и FDCAN.
Наличие блока не означает доступность нужного вывода на выбранной плате.
H503 [не поддерживает Arm TrustZone](https://wiki.st.com/stm32mcu/wiki/Security%3AHow_to_start_with_DA_access_on_STM32H503),
но имеет механизм доступа к отладке; не переносить на него security-конфигурацию H563.
Точные режимы и errata сверять по [RM0492/ES0561 на странице ST](https://www.st.com/en/microcontrollers-microprocessors/stm32h503/documentation.html).

| Этап | Что подготовить в IOC/адаптере | Проверка и отличие от F1/F4 |
| --- | --- | --- |
| GPIO/RCC/SysTick | SWD, LED по схеме; начать с внутреннего тактирования | Clock tree, voltage scale/Flash latency и частоты ADC/таймеров проверить заново; не переносить 8 МГц и битовые поля CFGR |
| ADC polling | Temperature/VREFINT, длительная допустимая выборка; сначала без DMA | Запуск регулятора/калибровка, готовность внутренних каналов, resolution/alignment; ранги/каналы/константы HAL перепроверить |
| ADC → GPDMA | Конечный буфер, completion/error IRQ; сначала без linked-list | Не использовать NDTR/CNDTR F4/F1. Сверить единицы длины HAL/блока GPDMA (байты/элементы), ширину данных, request routing, флаги и доступ к памяти |
| VDDA/температура | Читать калибровку H503 по CMSIS/LL и DS | В установленном CubeH5 V1.7.0 LL точки 30/130°C; текущая F411-функция зашивает 30/110°C, нужна параметризация и независимые векторы |
| TIM/LPTIM | Выбрать доступный таймер/IRQ и период по фактическому clock tree | Сначала IRQ, затем аппаратный trigger ADC; проверить маршрутизацию и debug freeze |
| RTC | Источник LSI/LSE по плате, alarm/wakeup, NVIC/EXTI | Реальная доставка события, повторный alarm, backup/reset и перенос даты; не копировать F1 IRQ-мост |
| PWR | Сначала Sleep, затем отдельный Stop с выбранным wake source | Доступ SWD, S_SLEEP/S_HALT, ход источника времени, сохранение SRAM/периферии, восстановление RCC; ток измерять без debug отдельно |
| CRC | Известные векторы, явные настройки polynomial/width/reversal | Не считать CRC контракт F1/F4 универсальным; reset/accumulate и порядок байтов |
| Позднее | DAC→ADC, comparator/OPAMP, I3C/FDCAN по доступным выводам | Для loopback проверить физическую разводку; I3C/FDCAN требуют подходящего внешнего устройства/трансивера и отдельного стенда |

Для GPDMA сначала подтвердить линейную передачу; linked-list, suspend/error и
синхронизацию нескольких каналов добавлять позднее. Требования к памяти/кэшу
выводить из H503 и расположения буфера, не копировать процедуры D-cache от других H5/H7.
Максимальную частоту MCU не использовать как начальную цель: сначала воспроизводимость.

### Критерий готовности профиля

Отдельные configure/build, корректный ELF и карта памяти; успешные проверки
GDB API/символов/HAL-контрактов; безопасные reset/run и верификация Flash; boot/GPIO,
ADC, GPDMA, timer и RTC на реальной плате; документированные пропуски и ограничения.
До этого статус h503cb — «план», не поддерживаемая цель. Конкретные числа/пины/маски
появятся в expectations после IOC и проверки источников, а не как копия F411.
