## Согласованная последовательность работ

Ближайший этап — обновление модуля и базовая регрессия STM32. Этапы ниже
выполняются последовательно, без привязки к срокам; при необходимости каждый
делится на отдельные проверяемые изменения. Это общий план интеграции и опытов:
реализация ядра, его схема и каноническая документация принадлежат stm32-gdbtest.

- [ ] 1. Обновить этот проект на новую фиксированную ревизию модуля: проверить
  обёртки и ссылки документации, собрать f103c8/f401cc/f411ce/f030r8/f429zi,
  выполнить host/prepare и согласованную аппаратную регрессию STM32.
  Результаты фиксировать с commit модуля/проекта, ELF и выбранным стендом.
  Промежуточный результат: `bc07625` после RC, пять сборок и host/prepare PASS;
  F411CE/ST-Link — OpenOCD22/22 и ST server22/22 PASS; WeAct BluePill-Plus,
  f103c8/J-Link — 22/22 PASS; F030R8/J-Link STLink — повторный набор17/17 PASS
  после окна SEGGER (первоначальный startup ERROR сохранён); F429ZI — OpenOCD22/22
  и ST server22/22 PASS. Остался F401CC; Nucleo после смены backend проверять отдельно.
  Подробности и ELF — docs/STATUS.md.
- [ ] 2. Добавить CI сборки и штатного `prepare` для пяти активных профилей:
  сначала один GCC, затем матрица toolchain; сохранять отчёты и артефакты.
  Проверки без оборудования не обозначать как аппаратный PASS. Подэтапы — ниже.
- [ ] 3. Оформить архитектурное решение о переносимости и новую схему профиля;
  сохранить чтение старых STM32-профилей. Разделить toolchain, архитектуру,
  MCU/memory/identity, backend и стенд; явно описывать доступные возможности.
- [ ] 4. Убрать ARM-зависимость из toolchain и обработки образов, включая
  полный ELF-контейнер; проверить на сохранённых ARM/RISC-V ELF без оборудования
  с отрицательными проверками границ, LMA и форматов.
- [ ] 5. Добавить JTAG и расширяемое описание J-Link/OpenOCD: device definitions,
  адаптер, transport, цепочка и lifecycle. Поддержка SEGGER Flash Loader
  не означает наличие соответствующего Flash-драйвера OpenOCD.
- [ ] 6. Запустить К1921ВГ015 через штатные CLI, `@case`, manifest, JSON/JUnit
  и recovery, используя [проверенный PoC](docs/K1921VG015_POC.md).
  Стенд разобран: перед HW требуется согласовать его сборку с владельцем.
  `examples/k1921vg015-errata` оставить отдельным измерительным примером.
- [ ] 7. Повторить STM32-регрессию и подключить второй RISC-V MCU, чтобы проверить
  общность адаптеров. Кандидат — GD32VF103; точную плату и backend согласовать.
  Следующие кандидаты: MDR1206FI, MIK32 и конкретные модели CH32V.
- [ ] 8. После двух разных RISC-V реализаций закрепить публичный интерфейс
  адаптеров и матрицу проверенных возможностей; не заявлять поддержку любого
  MCU только по наличию GCC или подключения GDB.
- [ ] 9. Затем развивать периферию по P1–P8, внешнее управление стендом
  и многоядерность; соответствующие задачи ниже остаются в плане.

H503 остаётся на паузе. Ограниченный опыт Renode + GDB-Python для startup/configuration
планировать отдельно от аппаратной регрессии; он не является условием поддержки RISC-V.

## CI этого репозитория: детализация этапа 2

Образец организации — [workflow stm32-hwtest-bluepill](https://github.com/ViacheslavMezentsev/stm32-hwtest-bluepill/blob/main/.github/workflows/ci.yml):
format, сборки по presets, проверки без платы, отдельный Renode smoke и артефакты.
Его прошивка использует CMSIS; здесь CubeMX/HAL и пять профилей, поэтому матрицу
и модели переносить с адаптацией. Ниже запланированные, ещё не реализованные проверки.

- [ ] CI-1. Подготовить воспроизводимое Linux-окружение: Ubuntu runner, CMake/Ninja,
  Python, xPack GCC с GDB-Python и нужные пакеты Cube; убрать зависимость CI от
  USERPROFILE и личных путей через presets/переменные окружения. Закрепить версии
  инструментов, SHA GitHub Actions и контрольные суммы загрузок; checkout подмодулей
  по gitlink. Предусмотреть кэш по версиям зависимостей и одинаковые команды локально
  и в GitHub; для Docker закрепить образ и описать локальный запуск.
- [ ] CI-2. Добавить workflow на push рабочих веток, pull_request и workflow_dispatch.
  Начать с одного GCC и пяти профилей f103c8/f401cc/f411ce/f030r8/f429zi, затем
  расширить до GCC 13/14/15. Собирать Debug и Release; штатный `prepare` выполнять
  для конфигураций с нужной отладочной информацией и подключёнными тестами.
  H503 и аппаратные эксперименты К1921 в эту STM32-матрицу не включать.
- [ ] CI-3. Отдельно проверять clang-format только для C/C++ в User (без изменений
  CubeMX/Core, Platform и подмодулей), ссылки документации и native-тесты арифметики.
- [ ] CI-4. Выполнять трассировку требований, ELF/manifest/contracts и штатные
  `prepare.*` через CTest без сервера и платы. Пересмотреть проектную offline-обёртку
  после обновления модуля; явно выбирать только проверки без оборудования.
- [ ] CI-5. Сохранять ELF/HEX/BIN/MAP, manifest, JSON/JUnit, логи сборок и подготовки
  при успехе и ошибке; связывать результаты с SHA проекта/подмодулей, preset и GCC.
  Обязательный ожидаемый тест/отчёт не должен незаметно отсутствовать при зелёном job.
- [ ] CI-6. Отдельным опытом добавить Renode smoke сначала для одного профиля:
  startup, достижение согласованной точки программы и фактическая конфигурация.
  Описать карту памяти, заглушки и границы доказательств; расширять матрицу только
  после проверки модели. У BluePill smoke использует UART и команды Renode, не GDB;
  наш вариант Renode + GDB-Python требует отдельного адаптера/проверки.
  Если необходима semihosting-телеметрия, выделить явную simulator-only сборку
  и подтвердить отсутствие этого кода в аппаратной прошивке. Не запускать набор
  аппаратных периферийных сценариев на заглушках и не обещать эмуляцию всех MCU.
- [ ] CI-7. Зафиксировать ожидаемый набор jobs и порядок проверки перед land:
  сборка, host/prepare и поддерживаемые emulator smoke должны завершиться для
  опубликованного SHA. Отсутствие Renode в обязательном emulator job — ERROR,
  а не молчаливое исключение теста. Первый полный прогон подтвердить в GitHub.

Аппаратный CI — отдельный будущий workflow с явным запуском на согласованном
self-hosted стенде. Обычный push/PR не должен подключаться к платам. Добавление
Renode не блокирует ввод полезного CI сборки и `prepare`.

## Будущее auto-gdbtest: Linux и совместные сценарии

Отложенное направление после общего ядра и полноценного RISC-V профиля.
`auto-gdbtest` — кандидат названия, переименование пока не выполняется.
DDTT сохраняет область тестирования внешнего целевого устройства; более общий
механизм сценариев может включать DDTT как часть системной проверки.

- [ ] 1. Подготовить общее ядро ARM/RISC-V по последовательности выше.
- [ ] 2. Поддержать один Linux-процесс через тот же базовый API: launch/attach,
  ELF/shared libraries, потоки, сигналы, завершение и восстановление.
- [ ] 3. Проверить две цели простым запросом/ответом без ROS: отдельный GDB-агент
  на цель и общий координатор в host Python, события/барьеры/таймауты,
  владение ресурсами, единый отчёт и завершение при отказе любой стороны.
- [ ] 4. Перенести опыт на ROS1-ноду Orange Pi 5 и bare-metal MCU с CRSF:
  сопоставить принятые, преобразованные и отправленные сообщения обеих сторон.
  Подход должен допускать другие протоколы, например MODBUS RTU.
- [ ] 5. Добавить внешние стимулы, захват канала и сценарии отказов. Различать
  буфер отправки, фактическую передачу и получение сообщения; учитывать влияние
  halt на очереди, протокольные таймауты и watchdog.

GDB API остаётся в главном потоке каждого GDB. Управляемые остановки и свободное
выполнение с наблюдением дают разные доказательства. Сначала одна выбранная
цель/ядро на GDB-сессию; многоядерные и разноархитектурные системы потребуют
отдельных правил выбора ядра, общей памяти, halt/reset и синхронизации.
