# Граница самостоятельного модуля и стендового проекта

Отделение завершено: [stm32-gdbtest](https://github.com/ViacheslavMezentsev/stm32-gdbtest)
имеет отдельную историю и подключается как `modules/stm32-gdbtest` с закреплённым
gitlink. Это основная форма поставки; pip/console executable пока не реализованы.
Версия runtime 0.1.0.dev0; правила релизов — [в модуле](../modules/stm32-gdbtest/docs/VERSIONING.md).

Модуль владеет runner/agent/Target, контрактами, backend, отчётами и CMake attach.
Этот проект владеет прошивкой, платами, MCU-профилями и сценариями требований.
Назначение проекта — проверять и помогать развивать независимый stm32-gdbtest.
Добавление обычного теста не требует изменения ядра.

Общий архитектурный обзор, практические методы и опыт совместимости остаются здесь.
Руководства механизмов перенесены в модуль; [карта документации](README.md).
История перехода и доказательства: [MODULE_SPLIT_PLAN](MODULE_SPLIT_PLAN.md),
[CONSUMER_VALIDATION](CONSUMER_VALIDATION.md). Исходный архитектурный документ сохранён.

При изменении ядра/его документации использовать отдельный checkout внутри разрешённого
workspace (например `.work/stm32-gdbtest`), собственную ветку и CHANGELOG модуля.
Сначала пользователь публикует коммит модуля, затем родительский gitlink, чтобы
другой потребитель смог получить зависимость. Build/temp/logs не писать в `modules`.
Рабочие checkout не являются build-артефактами и не удаляются обычной очисткой.
