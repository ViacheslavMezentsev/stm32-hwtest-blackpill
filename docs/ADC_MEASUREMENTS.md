# Измерения ADC: VDDA и температура кристалла

В `app_state` остаются сырые temperature_raw/vrefint_raw. После завершения DMA
основной цикл публикует `measurement.vdda_mv`, `temperature_mdeg_c`, `quality`,
затем увеличивает adc_sequences. Снимок читается на входе следующего loop;
остановка посреди публикации может дать смешанные поля. Это не атомарный протокол
для параллельного читателя, многопоточности в текущем приложении нет.

| quality | Значение |
| --- | --- |
| ADC_INVALID (0) | Непригодные входы/калибровка либо VDDA вне принятого окна; обе величины обнулены |
| ADC_TYPICAL (1) | F103: типовые параметры даташита; индивидуальная калибровка отсутствует |
| ADC_FACTORY (2) | F411: использованы валидные заводские отсчёты калибровки |

`quality` показывает способ расчёта, а не доказанную точность. Температура относится
к кристаллу, не к окружающему воздуху. Формат м°C нужен для целочисленной арифметики
и удобства сравнения; он не означает точности в тысячную градуса.

## F103

Источник: [ST DS5319](https://www.st.com/resource/en/datasheet/stm32f103tb.pdf),
таблицы Embedded internal reference voltage и Temperature sensor characteristics.
Используем типовые VREFINT=1200 мВ, V25=1430 мВ, Avg_Slope=4.3 мВ/°C.

Для отсчётов r=VREFINT, t=temperature:

- VDDA_mV = floor(1200 × 4095 / r).
- T_m°C = 25000 + trunc(((1430000 × r − 1200000 × t) × 1000) / (4300 × r)).

Температура вычисляется через отношение отсчётов: так округление VDDA до мВ не
добавляет ошибки. Знак наклона отрицательный. Аппаратная ADC self-calibration F1
остаётся в setup, но не заменяет индивидуальную калибровку температурного сенсора.
Типовые параметры допускают значительный разброс; без эталона это оценка.

## F411

Источник: [ST DS10314](https://www.st.com/resource/en/datasheet/stm32f411ce.pdf),
таблицы 72 и 75; адреса также сверены с `stm32f4xx_ll_adc.h` Cube F4 V1.28.3.
Platform читает uint16: VREFINT_CAL 0x1FFF7A2A, TS_CAL1 0x1FFF7A2C (30°C),
TS_CAL2 0x1FFF7A2E (110°C); все получены при VDDA=3300 мВ.

Обозначив эти значения c, a, b:

- VDDA_mV = floor(3300 × c / r).
- T_m°C = 30000 + trunc((t × c − a × r) × 80000 / ((b − a) × r)).

64-битные промежуточные произведения предотвращают переполнение; перед делением
проверяются r и b−a. Нулевые/насыщенные 12-битные входы и калибровки отвергаются,
как и b≤a. Оба варианта ограничены прикладным окном VDDA 2400…3600 мВ — это
политика этого примера, не универсальный диапазон всех STM32. Округление signed
деления выполняется к нулю; заведомо недопустимый выход int32 отвергается.

## Проверки и границы

На BluePill: 22/22 CTest PASS (20 HW + 2 host), в том числе реальные величины,
инъекции нуля/насыщения и восстановление, опорные 25°C при двух VDDA, −25°C и 100°C.
Пример реального наблюдения: 3289 мВ, 29361 м°C, quality=TYPICAL.
Инъекции меняют аргументы штатной функции через GDB, не вызывают функцию вручную.
Они подтверждают арифметику и публикацию, но обходят аналоговый тракт.

Native тест компилирует тот же User/Src/adc_units.cpp без HAL: опорные точки,
интерполяция, компенсация питания, отрицательная температура, непригодные
отсчёты и повреждённые калибровки. 1/1 CTest PASS, MinGW GCC 14.2.
В PowerShell, с CMake/Ninja и g++/его runtime DLL в PATH:

```powershell
Push-Location Tests/native
cmake --preset host
cmake --build --preset host
ctest --preset host
Pop-Location
```

Артефакты остаются в build/adc-native. Native тест отдельный, в check-hw не включён;
для смены host compiler использовать отдельный build. F411 прошивка собрана на
ARM GCC13, но новый аппаратный прогон пока не выполнен: подключена BluePill.
Далее требуется сравнение с внешними приборами, оценка погрешности/повторяемости
и аппаратная проверка заводской калибровки F411 после согласованной замены платы.
