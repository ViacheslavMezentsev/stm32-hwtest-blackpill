# F429ZI: устойчивость повторных запусков серверов

Опыт 2026-09-25, UTC run IDs 2026-09-24. DISCO/ST-Link V2J43S0/SWD,
OpenOCD0.12.0 и ST server7.14.0. Штатный Og ELF и модуль b76d909 не менялись.
Предыстория: [USB-сбой ST и переподключение](F429_STLINK_VALIDATION.md).

## Метод

Один HW_BOOT на каждый отдельный запуск CLI/сервера; последовательное выполнение,
явный serial, без одновременных клиентов. Максимум 24 запуска в серии,
остановка при первом ненулевом коде. MCU каждый раз reset/halt → main/loop →
reset_run; образ сравнивается, но при совпадении не записывается.
Серии отличаются backend или дополнительной паузой после возврата CLI.
«Без паузы» не означает нулевую задержку: между серверами есть подготовка runner.

Результаты/логи сохранены в build/f429zi-stability/runs, сводки
stlink-no-delay.json, openocd-no-delay.json и stlink-delay2.json.
Временная session.json меняет только каталог отчётов относительно штатной session.
Серийные номера и абсолютные персональные пути в Git не переносятся.

## Интерпретация и границы

Сбой не специфичен только для ST server или теста HW_ADC_INVALID: наблюдался
также до GDB в OpenOCD при повторении простого boot. Ошибка выбора serial
после успешных запусков не доказывает смену отладчика — чтение дескриптора
само завершилось ошибкой. Причина пока не локализована.

В коде runner сервер завершается taskkill /T /F после штатного завершения
GDB. Это потенциальный фактор lifecycle, но без контролируемого A/B опыта
его нельзя объявлять причиной. Отсутствие процесса не доказывает готовность
USB-устройства к следующему открытию. Кабель/порт/питание/firmware также пока
не исключены; последовательные серии не являются независимыми выборками:
вторая наследует состояние после первой и более ранних запусков.

Успешные 24 boot не доказывают устойчивость полного набора или отсутствие
редкой ошибки. Нельзя скрывать её автоматическим retry, менять ERROR на PASS
или объявлять паузу исправлением по одному успешному опыту. Число запусков
не является оценкой покрытия MCU или статистической надёжности.

## Следующие контролируемые опыты

При повторении: один backend на свежем USB-подключении, одинаковый порядок
сценариев, отдельно проверять паузу, затем кабель/USB-порт с согласованием
владельца. Сохранять исходный первый сбой и не продолжать длинную серию ошибок.
Сравнение штатного завершения серверного процесса с принудительным требует
отдельной доработки/проверки модуля, с сохранением внешних timeout и recovery.
Firmware отладчика, option bytes и глобальные USB-настройки автоматически не менять.
