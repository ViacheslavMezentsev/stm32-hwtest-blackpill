# К1921ВГ015: проверка from_chars и errata, 2026-09-24

## Вопрос и границы доказательства

Проверяется сообщение о том, что готовая `libstdc++.a` содержит небезопасное
соседство `flw` и `fdiv.s`, а `-mfix-cloudbear-0001` у приложения его не устраняет.
Официальная [errata от 15.04.2026, пункт 5, страница 4](https://niiet.ru/wp-content/uploads/2026/04/errata_K1921VG015_Rev4_lqfp100.pdf)
связывает сбой итеративных инструкций с задержанной загрузкой операнда из Flash.
Производитель рекомендует вставку NOP или соответствующий ключ своего GCC.
Источник актуального документа — [страница MCU](https://niiet.ru/product/к1921вг015/).

Пакеты перечислены на [CloudBEAR Tools](https://tools.cloudbear.co/).
Испытан **Windows-пакет CloudBEAR 14.1.0.7**, предоставленный владельцем,
и два установленных Windows xPack. Архив **CentOS 8** из сообщения не получен:
зеркало было недоступно. Побитовое совпадение Windows/Linux библиотек не утверждается.
Не проверены все функции libstdc++, libc/libm/libgcc и все инструкции пункта 5.
Наличие дефектного участка не позволяет установить полную историю флагов сборки архива.

## Методика

Стенд: тот же К1921ВГ015, CHIPID `0xDEADBEE1`, J-Link EDU v11, JTAG 1000 kHz,
server 8.32; GDB 15.1/Python 3.12.2 из xPack 13. Частота по `SystemCoreClock` —
50 MHz. CHIPID не используется для отождествления его младшего поля с названием
Rev.4 на обложке errata. Факт сбоя установлен на конкретном подключённом экземпляре.

Отдельное [приложение](../examples/k1921vg015-errata/README.md) использует
read-only SDK прежнего [PoC](K1921VG015_POC.md). Это специально согласованный
диагностический firmware, а не тестовый hook в обычном blink. Сборка `-Og -g3`,
hard-float ABI `ilp32f`, полная `libstdc++.a`, без `nano.specs` и LTO.
CloudBEAR компилирует приложение и SDK с `-mfix-cloudbear-0001`.

Каждый сценарий делает 1000 вызовов:

1. `std::from_chars("1e-5", ..., float, general)`; ожидаемые биты `0x3727C5AC`.
2. Явный inline asm: `flw` из Flash непосредственно перед `fdiv.s`, 1/100000.
3. Тот же asm с `nop` между загрузкой и делением.
4. Тот же asm без nop с операндом в RAM.

Считаются неверные биты, положительная бесконечность `0x7F800000`, ошибки `ec`
и неверная конечная позиция `ptr`; сохраняются первый, последний и первый неверный
результаты. IRQ специально не включаются. GDB не делает single-step и не ставит
breakpoint внутри расчётов: единственная аппаратная остановка — после всей серии.
JTAG всё же подключён; автономный опыт после физического отсоединения не выполнен.

Два дополнительных build перемещают `.rodata`/`.rodata.*` в инициализированную
`.data`; библиотечный код и архив не меняются. Post-link проверяет адрес таблицы,
GDB — значение её элемента [5] (`100000`, биты `0x47C35000`). Это контроль с
расходом RAM и изменением layout, а не исправление всех библиотек. `.srodata`
не перемещается. В RAM-build также переезжает названный `flash_divisor`.

## Компилятор и готовая библиотека

| Пакет | Выбранный multilib | Ключ обхода |
| --- | --- | --- |
| xPack 13.3.0-2 | `rv32imf_zicsr/ilp32f` | отклонён компилятором |
| xPack 14.2.0-3 | `rv32imf_zicsr/ilp32f` | отклонён компилятором |
| CloudBEAR 14.1.0.7 (GCC 14.1.0) | `rv32imfc_zicsr_zifencei_zba_zbb_zbc_zbs/ilp32f` | принят |

Для CloudBEAR требуется полный march из таблицы: сокращённый вариант xPack
выбирал RV64-библиотеки и закономерно не линковался с RV32. Не обходить эту
ошибку принудительной линковкой несовместимого ABI.

Независимая C-проба `return x / *p`, `-O2`, CloudBEAR:

```asm
# без ключа                # с -mfix-cloudbear-0001
flw    fa5,0(a0)           flw    fa5,0(a0)
fdiv.s fa0,fa0,fa5         nop
ret                       fdiv.s fa0,fa0,fa5
                          ret
```

Но в **итоговом ELF** приложения CloudBEAR с этим ключом:

```asm
800031c2: 6398       flw    fa4,0(a5)
800031c4: 18e7f7d3   fdiv.s fa5,fa5,fa4
```

Участок принадлежит `std::from_chars(... float& ...)` из
`libstdc++.a(floating_from_chars.o)`; таблица находится по `0x80022FB0` во Flash.
У xPack 13 та же пара по `0x800039C0/0x800039C4`, у xPack 14 —
`0x80003B98/0x80003B9C`. Таким образом, обход реально работает при компиляции
пробы, но не переписывает уже собранный библиотечный объект. Inline asm также
остаётся ответственностью автора — компилятор не вставляет nop внутрь нашей строки.

## Варианты обхода

Приоритет: исправленные библиотеки вместе с ключом компилятора; если это пока
невозможно — адресный обход с доказательством в итоговом ELF и аппаратным регрессионным
тестом. Статус ниже относится только к описанному опыту, а не к сертификации решения.

| Вариант | Что меняет | Статус и ограничения |
| --- | --- | --- |
| CloudBEAR `-mfix-cloudbear-0001` | Вставляет nop при генерации затронутого кода | На C-пробе подтверждено. Нужен при компиляции всех затронутых C/C++ единиц, включая библиотеки; флаг только на этапе линковки недостаточен. Inline asm и готовые объекты требуют отдельной проверки. |
| Пересборка libstdc++, newlib/libm, libgcc с обходом | Устраняет источник проблемы в повторно используемом коде | Рекомендуемый системный путь; в этом опыте библиотеки не пересобирались. Нужны совместимые исходники, ISA/ABI/multilib и аудит ассемблера; проверить, какой архив реально выбрал linker. |
| `-mno-fdiv` | Запрещает компилятору генерировать аппаратные FP divide/sqrt | Проверена генерация вызова `__divsf3` в C-пробе CloudBEAR. Не меняет уже готовый from_chars; helper/libm тоже должны быть проверены. Полная сборка/HW этого варианта не выполнялись. |
| `-mno-div` | Убирает аппаратное целочисленное деление из вновь генерируемого кода | C-проба CloudBEAR вызывает `__divsi3`. Нужно отдельно проверять остаток, helpers и готовые архивы; FP и clmul этим не исправляются. |
| ISA без F/D, ABI `ilp32` | Переход на программную FP-арифметику | Компиляция C-пробы с `rv32imc_zicsr_zifencei/ilp32` проверена, получен `__divsf3`. Нужны согласованные startup/все объекты/библиотеки; одной смены ABI при сохранении F недостаточно. Софт-FP может использовать затронутые целочисленные инструкции. |
| ISA без Zbc и других расширений с carry-less multiply, если они включены | Исключает автоматическую генерацию clmul из новых единиц трансляции | Кандидат для соответствующей части errata, здесь аппаратно не проверен. Не исправляет asm/готовые архивы; не смешивать с запретом обычного multiply. |
| Таблица/константы в RAM | Устраняет Flash-загрузку перед операцией | Для from_chars проверено на xPack 14 и CloudBEAR: 0/1000. Расходует RAM, требует инициализации и проверки VMA/LMA; перенос одной таблицы не защищает другие пути. |
| `load; nop; iterative-op` в одном asm-блоке | Явно разделяет инструкции | На прямом fdiv-контроле проверено, 0/1000 с nop. Остальные инструкции пункта 5 требуют собственных тестов. |

Назначение стандартных ключей и связь ISA/ABI описаны в
[GCC RISC-V Options](https://gcc.gnu.org/onlinedocs/gcc-14.3.0/gcc/RISC-V-Options.html).
Наличие конкретного ключа проверять установленным компилятором: vendor-опция
CloudBEAR отсутствует в двух исследованных xPack. `-mno-fdiv` не означает полный
soft-float: ABI может остаться `ilp32f`, остальные FP-инструкции разрешены.
Полный отказ от аппаратного divide/rem обычно требует более строгой ISA и/или
пересборки helpers; `-mno-div` у приложения сам по себе этого не доказывает.

### Точечные программные приёмы

**RAM-копия данных.** Для собственных констант можно организовать изменяемую
таблицу в `.data` либо копировать её в RAM при старте. Для библиотеки выбрать
конкретную входную секцию linker script или изменить её исходник. После линковки
проверить реальный адрес и чтение из RAM. Обычная локальная переменная `float t =
const_value` не гарантирует перенос: оптимизатор может вернуть константу в Flash
или вообще заменить вычисление. Даже `volatile` сам по себе не вставляет nop:
volatile-объект должен действительно находиться в RAM.

**Asm-обёртка операции.** Минимальный шаблон для reviewed участка:

```cpp
float result;
asm volatile("flw ft0, 0(%1)\n\t"
             "nop\n\t"
             "fdiv.s %0, %2, ft0"
             : "=f"(result) : "r"(denominator), "f"(numerator)
             : "ft0", "memory");
```

Здесь загрузка, nop и деление находятся в одном блоке, с описанными operand/clobber.
Это шаблон для ABI/ISA с F, его нужно проверить в своём ELF. Он не перехватывает
деление внутри `std::from_chars`. Отдельный `asm("nop")` рядом с выражением C,
пустой compiler barrier или `nop` перед вызовом функции — недостаточный контракт
расположения машинных инструкций. В эксперименте используется эквивалентная
обёртка с фиксированным числителем, её код и результат проверены на плате.

**Замена конкретного алгоритма.** Если входной формат узкий, можно написать
ограниченный десятичный parser: накопление цифр, явный контроль переполнения,
масштабирование через проверенные RAM-константы/операции. Для фиксированной
точности можно оставить результат целым числом в заданных единицах, вообще
не преобразуя в float. Требуется определить поддержку знака, экспоненты,
округления, диапазона, NaN/Inf и ошибок. Это не полноценная замена from_chars
без дополнительных тестов. Замена на `strtof`, `sscanf` или `double` сама по себе
не доказывает обход: внутри другой библиотеки могут быть затронутые инструкции.

**Умножение вместо деления на известную константу.** Для ограниченной задачи
можно умножать на заранее вычисленную обратную величину. Это меняет округление,
поведение крайних значений и иногда точность. Нужно исключить runtime-деление
при вычислении самой обратной величины и проверить, что оптимизатор не вернул
деление. `-ffast-math` не является универсальным средством обхода и меняет
численный контракт; в проверенных сборках он не включён.

**Пересборка только затронутого объекта/функции.** Возможна при наличии исходников
точной версии библиотеки: исправить/пересобрать floating_from_chars и осознанно
заменить объект в частном архиве либо применить собственную реализацию. Проверять
ODR, имена символов C++, зависимости и итоговую map. Это меньше полной пересборки,
но защищает только проверенный путь. Прямое добавление байтов nop в готовый ELF
смещает инструкции, переходы и релокации; произвольный бинарный патч не применять.
Нужен полноценный контролируемый binary rewriting или пересборка.

**Перенос кода в RAM.** Сам по себе не устраняет Flash-операнд. Может изменить
тайминги и проявление дефекта, но не считается обходом без переноса данных либо
разделения инструкций. Аналогично успешный single-step, снижение частоты,
изменение выравнивания, `-O0`, `-fno-builtin`, `-fno-schedule-insns`, fence или
увеличение паузы между вызовами не заменяют доказанного nop на нужном месте.
Эти варианты здесь не проверены как исправление. Не стоит пытаться «лечить»
ошибку повторным вызовом до приемлемого результата: неверное конечное число
может выглядеть правдоподобно и пройти такой фильтр.

Для нашего прототипа разумно сохранить два уровня регрессии: анализ опасных
участков итогового ELF и аппаратный тест с чувствительным входом и контрольным
обходом. Проверять не только +inf, но и любые несовпадающие биты/контракт округления.

## Практический вывод для тестового модуля

Совместимость включает предсобранные архивы, выбранный multilib, размещение данных
и errata конкретного MCU; одних версии GCC и успешной сборки недостаточно.
Для такого теста нужны воспроизводимый ELF, hash библиотек, анализ машинного кода,
контроль RAM/nop и непрерывное выполнение критического участка до наблюдения.
Скорость JTAG или число тестов не дают гарантии покрытия errata.

Практический путь исправления — проверенная пересборка затронутых библиотек
совместимым toolchain с обходом и аудит ассемблерных участков. Перенос выбранных
констант в RAM возможен как адресный обход после проверки итогового ELF;
данный опыт не объявляет его универсальным решением. `nop` в вызывающем коде
перед вызовом `from_chars` не разделяет инструкции внутри библиотеки.

## Воспроизводимость и неуспешные попытки

Presets и `series.py` описаны в README примера. `inspect.py <build>` сохраняет
`linked.dis`, `inspection.json` и C-пробу ключа. Отчёты, ELF/BIN/manifest,
снимок GDB-agent, полный Flash readback и логи — внутри `build`, не в Git.
`OBSERVED` означает завершённый опыт, а не успешную арифметику.

Первые загрузки C++-образов превысили предел blink-runner 45 секунд и завершились
`ERROR`; recovery и восстановление blink прошли. Диагностический предел увеличен
до 300 секунд. Первоначальный linker EXCLUDE_FILE не перенёс таблицу; это выявлено
по адресам, такие запуски не считаются RAM-контролем. Добавлена обязательная
post-link проверка размещения. Один промежуточный запуск использовал старый ELF
с новой схемой счётчиков и завершился ERROR; итоговые запуски используют снимки
agent и совпадающие ELF/manifest. Неполные результаты не включаются в итоговую таблицу.

Ранний вариант с менее подробными счётчиками показал для from_chars 2/1000 ошибок
на xPack 13, 1000/1000 на xPack 14 и 1/1000 на CloudBEAR. Простой asm при этом
часто не воспроизводил сбой. Добавление диагностики меняет layout и наблюдаемую
частоту: это не измерение вероятности ошибки в другом приложении и не доказательство
конкретной причины изменения частоты (кэш/выравнивание отдельно не исследовались).
