# Практика тестирования STM32 через отладчик

Это развиваемая основа будущей отдельной системы hwtest. Здесь фиксируем методы,
эксперименты, границы доказательства и решения для общего API. Архитектурное
предложение находится в [HWTEST_ARCHITECTURE.md](HWTEST_ARCHITECTURE.md), команды
текущей реализации — в [HWTEST.md](HWTEST.md). Наличие метода в этом документе
не означает его реализации или проверки на всех STM32.

## Цель и критерий полезности

Подключаемый механизм должен брать на себя запуск инструментов, владение стендом,
прошивку, управление исполнением, диагностику и отчёты. Проект добавляет Python-тесты,
требования и описание MCU/стенда. Проверка считается полезной, если указаны:
требование, стимул, наблюдаемая величина, независимое ожидаемое значение,
точка наблюдения, влияние отладчика и непокрытая часть поведения.

«Без тестового кода в прошивке» не означает отсутствие вмешательства: breakpoint
меняет временное поведение, чтение некоторых MMIO-регистров имеет побочный эффект,
подмена аргумента меняет исполнение. Эти вмешательства нужно различать в отчётах.

## Что взято из 99_BOARD_TEST

Изучены 20 Python-сценариев `Tests/BBC_SW_LLR`: девять BOARD_TEST_01 (ADC), пять
BOARD_TEST_02 (UART), четыре BOARD_TEST_03 (SPI), два BOARD_TEST_10 (RCC).
Это источник приёмов, а не готовые тесты F411: состав периферии, HAL-структуры,
тактовые частоты и соединения другой платы нельзя переносить автоматически.
Соседний проект не изменялся и его аппаратные сценарии здесь не запускались.

| Примеры в BBC_SW_LLR | Полезный приём | Решение для нашего модуля |
| --- | --- | --- |
| 01_01, 01_08, 02_01, 03_01 | Проверка полей handle после init | Именованные сравнения вместо одного `all`; отдельно проверять регистры и поведение |
| 01_03…01_07, 01_09 | Условие по handle, каналу и рангу | `reach(function, when=...)`; для нескольких вызовов выбирать конкретный экземпляр |
| 02_04, 03_04 | Проверка GPIO_Init на входе HAL | `fields("*GPIO_Init", {...})`; затем наблюдать применённую настройку |
| 01_02, 02_02, 03_02, 10_02 | Подмена указателя на NULL | `set_value`; сначала проверить исходник HAL на обработку NULL до разыменования |
| 01_03…01_07, 01_09 | Принудительный HAL_ERROR | `force_return`; отметить, что тело HAL пропущено |
| 02_03, 03_03 | Проверка RCC после MSP init | Читать безопасные регистры/поля; доступность макросов зависит от debug info |
| 02_05 | Проверка deinit и наличия символа | Отсутствующий обязательный символ — ERROR; недостижимый deinit требует отдельного сценария приложения |
| 10_02 | Проверка бесконечного цикла по инструкции | Оставить для специальных тестов конкретного ELF; не использовать как переносимый критерий |

Замеченные ловушки примеров:

- В 01_08 выражение `hadc2.Init.ContinuousConvMode = ENABLE` присваивает значение.
  Новый `fields` сравнивает отдельно полученные actual/expected, однако выражения
  GDB всё равно доверенные: API не является анализатором C и не запрещает все побочные эффекты.
- В 03_04 и некоторых других заголовках ID не соответствует имени файла.
  В текущем модуле ID требований и тестов сверяются автоматически.
- `except Exception` с единственным false теряет причину. Нужны FAIL/ERROR,
  traceback, значения и причина остановки.
- `return` уже убирает текущий кадр; следующий `finish` исполняет вызывающую функцию.
  Безусловное копирование цепочки `return; finish` меняет смысл теста.
- `b.n` и конкретный opcode зависят от генерации кода. Попадание в Error_Handler
  не доказывает отдельно отключение IRQ и бесконечность дальнейшего исполнения.

Семантика `return` и отличие от `finish` описаны в
[руководстве GDB](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Returning.html).
В архитектурном эскизе комментарий `force_return: return + finish` следует считать
устаревшим: текущий API выполняет только `return`.

## Каталог методов и границ

| Метод | Что подтверждает, сильная сторона | Ограничения и цена | Статус здесь |
| --- | --- | --- | --- |
| Чтение handle/аргументов HAL | Контракт вызова, выбор экземпляра, канала, режима; удобные имена | Handle — намерение ПО, не доказательство записи в MCU; locals могут исчезнуть при оптимизации | GPIO arguments проверен |
| Чтение RCC/GPIO после init | Итоговую цифровую конфигурацию | Не доказывает форму сигнала; сверять семантику чтения и маски в RM | RCC/GPIO проверены |
| Условный breakpoint | Нужный повторный вызов; минимум точек в тесте | Условие может проверяться хостом с остановкой при каждом попадании; влияет на время | Выбор второго TogglePin проверен |
| Следующая известная точка программы | Наблюдение эффекта после вызова без хрупкого номера строки | Между вызовом и точкой есть другой код; выбирать точку с однозначной причинностью | TogglePin → loop проверен |
| finish / FinishBreakpoint | Наблюдение возврата и его значения | Не применять вслепую после return, к ISR, inline/tail-call; валидировать кадр и событие | Общего API пока нет |
| Подмена аргумента/памяти | Ошибочные входы, границы, обработку внутри настоящего HAL | Только при понятных предусловиях; состояние искусственное, не физический отказ | NULL для обеих RCC-функций проверен |
| force_return | Ветку реакции вызывающего кода на HAL_ERROR/TIMEOUT/BUSY | Тело и эффекты HAL пропущены; правильный тип возврата зависит от ABI/debug info | RCC HAL_ERROR проверен |
| Hardware watchpoint | Доступ CPU к выбранной переменной/адресу | Ограниченные компараторы; нельзя считать универсальным наблюдателем записей DMA | Планируется |
| Буфер DMA после завершения | Результат передачи, длину, порядок, данные | Остановка CPU не гарантирует остановки DMA; нужен момент завершения и владение буфером | Планируется |
| IRQ/callback | Достижение обработчика, флаги, состояние ПО | Breakpoint искажает latency; несколько ожидающих IRQ могут изменить порядок | Планируется |
| Внутренний loopback/программный trigger | Часть цифрового пути без внешних проводов | Возможность зависит от конкретного периферийного блока; не покрывает внешний тракт | Планируется |
| Внешний генератор/loopback/анализатор | Входы, выходы, протокол и реальное время | Дополнительное оборудование, независимые измерения и синхронизация | Нет в текущем стенде |
| Trace/SWO/ETM | Поток событий при меньшем вмешательстве | Поддержка MCU, корпуса, выводов, пробника, инструмента; не универсальная возможность | Не проверено |
| Host unit tests | Чистую логику, комбинации и граничные значения быстро | Не проверяет реальную периферию | Есть для инфраструктуры |

Условия GDB допускают побочные эффекты и функции. В тестах используем только
выражения без записи и вызова функций; после остановки `reach` повторно проверяет
условие, чтобы не принять остановку из-за ошибки его вычисления за успех.
[GDB: Break Conditions](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Conditions.html).

## Практический API и рецепты

Реализовано на Debug `-Og -g3`, GCC 13.3.1, GDB 14.2.90/Python 3.11.4:

```python
t.reach("HAL_GPIO_Init", when="GPIOx == GPIOC")
t.fields("*GPIO_Init", {"Pin": "GPIO_PIN_13", "Mode": "GPIO_MODE_OUTPUT_PP"})
t.reach("loop")
t.check("PC13 output", (t.value("GPIOC->MODER") >> 26) & 3, 1)
```

`fields` принимает целочисленные/указательные поля, ожидаемые числа либо C-выражения,
останавливается на первом несовпадении и сохраняет имя/actual/expected.
Float, массивы, допуски и сбор всех несовпадений пока не реализованы.
Макросы доступны в этом ELF благодаря `-g3`; при отсутствии макроса — ERROR,
а не подстановка нуля. Не надо выводить ожидаемое значение из того же actual.

```python
t.reach("HAL_RCC_ClockConfig")
t.set_value("RCC_ClkInitStruct", "0")
t.check("NULL injected", t.value("RCC_ClkInitStruct"), 0)
t.reach("Error_Handler")
```

В используемом Cube F4 V1.28.3 обе функции RCC явно возвращают HAL_ERROR при NULL.
`set_value` сохраняет before/after, `force_return` — имя функции и заданный возврат
в `mutations` JSON. После каждого теста reset/run восстанавливает штатное состояние.
Применимость к другим версиям HAL проверять по исходникам заново.

Рабочие рецепты находятся в [test_peripheral_methods.py](../Tests/board/test_peripheral_methods.py).
Для ADC этот же шаблон может выбирать `hadc` + канал + ранг и проверять структуру
на входе HAL, но реальное преобразование требует отдельного источника/эталона.
Для SPI/UART проверка init должна дополняться передачей известных данных и проверкой
ошибок/таймаутов; чтение handle не заменяет эту часть. Для DMA сначала определить
момент окончания, ownership и при наличии cache — правила согласования памяти.

## Что нельзя заключить из остановок GDB

1. Нельзя получить достоверную latency/jitter непрерывно работающего приложения,
   регулярно останавливая CPU. HAL tick — программная шкала; не эталон частоты.
2. Нельзя доказать аналоговую точность ADC или качество фронтов GPIO/SPI по handle
   и регистрам. Нужен независимый физический стимул/измеритель.
3. Нельзя считать остановку ядра общей остановкой периферии. Для F411 изучать
   DBGMCU и freeze-настройки конкретных таймеров/watchdog в
   [RM0383, раздел Debug support](https://www.st.com/resource/en/reference_manual/rm0383-stm32f411xce-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).
   Политику freeze нужно фиксировать как условие опыта, не менять молча.
4. Нельзя переносить схему fault-регистров, число breakpoints и доступность trace
   между Cortex-M0/M4/M7/M33. Это свойства целевого MCU/ядра/доступа, а не общего Python API.
5. Нельзя гарантировать наблюдение удалённой компилятором переменной. Сначала
   проверить символы/места breakpoint и DWARF; для Release выбирать другие точки
   либо явно объявлять невозможность данного наблюдения.
6. Нельзя читать все MMIO «для диагностики»: встречаются read-to-clear, FIFO/data,
   зарезервированные адреса. SVD полезен, но требует сверки с RM и errata.
7. Нельзя вызвать несуществующую в ELF функцию deinit. Прямой `gdb call` существующей
   функции — другой эксперимент: он меняет контекст/стек, может ждать IRQ/тик или
   блокировку и не доказывает штатную достижимость пути приложения.

## Покрытие: несколько независимых измерений

Число зелёных тестов и совпадение ID требований не являются процентом покрытия кода.
Сейчас есть трассируемость заявленных требований, но нет счётчика statement/branch/MC/DC.
Разделяем следующие матрицы:

- Требования: перечисленные требования × позитивный сценарий × граничные случаи × ошибки.
- Периферия: init/config × работа × IRQ/DMA × ошибки/timeout × deinit/reinit × reset/recovery.
- Конфигурации: MCU/revision × HAL/version × compiler/optimization × probe/backend.
- Доказательство: контракт ПО × состояние регистров × результат выполнения × физическое измерение.

Для каждого незакрытого пункта записывать причину: нет сценария в приложении,
нет стимула/оборудования, нет наблюдаемости, ограничение MCU, тест ещё не написан.
Различать «не применимо» и «не проверено». Отсутствующий стенд/символ обязательного
сценария сейчас ERROR; в будущем SKIP должен иметь явную capability-причину.

Максимальное обоснованное покрытие достигается сочетанием host-проверок логики,
аппаратных проверок контрактов/регистров, управляемых инъекций и внешних измерений.
Структурное покрытие потребует отдельного способа измерения (инструментированная
сборка или поддерживаемая трассировка) с описанием его влияния на объект проверки.
Нельзя объявлять 100% branch coverage из факта попадания в несколько функций.

Текущее покрытие BlackPill:

| Область | Доказано тестами | Остаётся |
| --- | --- | --- |
| Boot | main → loop | startup fault/recovery, варианты reset |
| RCC | HSI/делители, HAL_ERROR и NULL в двух вызовах | timeout готовности, физическая точность частоты |
| GPIO | Аргументы init, регистры PC13, два переключения, выбор повторного вызова | Электрический уровень, другие режимы/пины, EXTI |
| Время | Изменение uwTick между проходами | IRQ latency, jitter, независимое измерение периода |
| ADC/SPI/UART/TIM/DMA | Не проверены этой прошивкой | Рабочий сценарий приложения и подходящий стимул |

## Журнал экспериментов

Каждая следующая запись должна содержать конфигурацию, метод, проверяемое утверждение,
позитивный и негативный контроль, результат, ограничения и ссылку на тест/отчёт.

### E01: контракт GPIO и выбор повторного вызова

BlackPill F411, ST-Link/OpenOCD 0.12, Debug GCC13, прошивка без изменений.
`HW_GPIO_ARGUMENTS` и `HW_GPIO_FILTERED_CALL` — PASS. Условие пропускает первый
TogglePin с ODR13=0 и выбирает следующий с ODR13=1; после вызова ODR13=0.
Неверное ожидаемое Mode=INPUT даёт FAIL с именем поля. Условие `0` даёт ERROR
по внешнему таймауту 2 с и host recovery; неизвестный аргумент даёт ERROR GDB.
Это подтверждает выбор вызова и цифровое состояние, но не качество сигнала.

### E02: естественный путь ошибки HAL

`HW_RCC_OSC_NULL` и `HW_RCC_CLOCK_NULL` — PASS с before/after в mutations.
Обе ветки выполняют проверку NULL в реальном HAL и достигают Error_Handler.
Для сравнения `HW_RCC_ERROR` принудительно возвращает ошибку без выполнения HAL.
Ни один сценарий не имитирует физическую неисправность HSI или аппаратный timeout.

Совместный прогон: 11/11 CTest (9 аппаратных и 2 host, один из них содержит 7 unit tests).
JSON/JUnit и SHA ELF находятся в `build/debug-hwtest/hwtest`, отрицательные опыты —
`build/method-negative`. Артефакты локальные, в Git не включаются.

Отрицательные примеры сохранены в [Tests/experiments](../Tests/experiments/test_api_negative.py)
и намеренно исключены из обычного CTest. Повторение из корня проекта после сборки:

```powershell
New-Item -ItemType Directory -Force build/method-negative | Out-Null
$session = Get-Content build/debug-hwtest/hwtest/session.json -Raw | ConvertFrom-Json
$session.tests = (Resolve-Path Tests/experiments).Path
$session.out = Join-Path (Resolve-Path build/method-negative).Path 'runs'
$json = $session | ConvertTo-Json
$destination = Join-Path (Resolve-Path build/method-negative).Path 'session.json'
[IO.File]::WriteAllText($destination, $json, [Text.UTF8Encoding]::new($false))
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_BAD_FIELD
# Ожидается exit 1, FAIL, имя поля Mode.
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_FALSE_CONDITION --timeout 2
# Ожидается exit 2, ERROR, host recovery.
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_INVALID_CONDITION
# Ожидается exit 2, ERROR, неизвестный символ.
ctest --preset hw -R '^hw.HW_BLINK$'
# После отрицательных контролей штатный тест должен пройти.
```

## Граница будущего самостоятельного модуля

| Общая система | Профиль MCU/платы | Проектные Python-тесты |
| --- | --- | --- |
| Оркестратор, lifecycle, блокировки, timeout, отчёты, сбор тестов | Flash/RAM, загрузочные регионы, reset, fault-регистры/символы, breakpoint budget | Требования, ожидаемые поля/режимы, точки наблюдения, стимулы |
| GDB API исполнения/наблюдения/инъекций | Периферийные capabilities, MMIO read policy, debug freeze, multicore/security/cache | Последовательности ADC/SPI/DMA и собственная логика |
| Адаптеры серверов и контракты их готовности | Probe/serial/соединения и безопасное состояние выхода | Независимые ожидаемые результаты и границы покрытия |

Нынешний hwtest ещё содержит F411-зависимости: 0x08000000/512 KiB, четыре fault-handler,
шесть breakpoint, CFSR/HFSR, конфигурацию OpenOCD, reset/run, resource lock BlackPill.
Также CMake и runner предполагают расположение модуля в корне проекта, один ELF
и Windows. Копирование каталога пока не равно переносимой системе для любых STM32.

Следующие этапы без привязки ко времени:

1. На опытах уточнять API ожидания события/возврата, операций с полями и инъекций;
   сохранять отрицательные контроли, не скрывать gdb.error за false.
2. Вынести перечисленные зависимости в проверяемый профиль цели и параметры
   hwtest_attach; разделить корень модуля, проекта и каталог артефактов.
3. Проверить один сценарий IRQ и один DMA/таймерный сценарий с явным учётом halt/freeze;
   для этого сначала определить полезное поведение прошивки, затем её тесты.
4. Проверить отдельный проект-потребитель внутри этого workspace, затем второе семейство
   при наличии оборудования. До этого заявлять поддержку только проверенного F411.
5. После подтверждения границ выделить пакет/репозиторий, версии конфигурации и API,
   пример подключения; добавить другие backends и CI по реальной необходимости.

Не включаем всё семейство STM32 посредством одной таблицы адресов: Cortex, Flash,
debug, безопасность и периферийные блоки требуют отдельных проверяемых возможностей.
