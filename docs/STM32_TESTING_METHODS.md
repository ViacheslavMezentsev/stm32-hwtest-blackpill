# Практика тестирования STM32 через отладчик

Это развиваемая основа будущей отдельной системы hwtest. Здесь фиксируем методы,
эксперименты, границы доказательства и решения для общего API. Архитектурное
предложение находится в [HWTEST_ARCHITECTURE.md](HWTEST_ARCHITECTURE.md), команды
текущей реализации — в [HWTEST.md](HWTEST.md). Наличие метода в этом документе
не означает его реализации или проверки на всех STM32.

## Цель и критерий полезности

Подключаемый механизм должен брать на себя запуск инструментов, владение стендом,
прошивку, управление исполнением, диагностику и отчёты. Проект добавляет Python-тесты,
требования и описание MCU/стенда. Проверка считается полезной, если указаны:
требование, стимул, наблюдаемая величина, независимое ожидаемое значение,
точка наблюдения, влияние отладчика и непокрытая часть поведения.

«Без тестового кода в прошивке» не означает отсутствие вмешательства: breakpoint
меняет временное поведение, чтение некоторых MMIO-регистров имеет побочный эффект,
подмена аргумента меняет исполнение. Эти вмешательства нужно различать в отчётах.

## Что взято из 99_BOARD_TEST

Изучены 20 Python-сценариев `Tests/BBC_SW_LLR`: девять BOARD_TEST_01 (ADC), пять
BOARD_TEST_02 (UART), четыре BOARD_TEST_03 (SPI), два BOARD_TEST_10 (RCC).
Это источник приёмов, а не готовые тесты F411: состав периферии, HAL-структуры,
тактовые частоты и соединения другой платы нельзя переносить автоматически.
Соседний проект не изменялся и его аппаратные сценарии здесь не запускались.

| Примеры в BBC_SW_LLR | Полезный приём | Решение для нашего модуля |
| --- | --- | --- |
| 01_01, 01_08, 02_01, 03_01 | Проверка полей handle после init | Именованные сравнения вместо одного `all`; отдельно проверять регистры и поведение |
| 01_03…01_07, 01_09 | Условие по handle, каналу и рангу | `reach(function, when=...)`; для нескольких вызовов выбирать конкретный экземпляр |
| 02_04, 03_04 | Проверка GPIO_Init на входе HAL | `fields("*GPIO_Init", {...})`; затем наблюдать применённую настройку |
| 01_02, 02_02, 03_02, 10_02 | Подмена указателя на NULL | `set_value`; сначала проверить исходник HAL на обработку NULL до разыменования |
| 01_03…01_07, 01_09 | Принудительный HAL_ERROR | `force_return`; отметить, что тело HAL пропущено |
| 02_03, 03_03 | Проверка RCC после MSP init | Читать безопасные регистры/поля; доступность макросов зависит от debug info |
| 02_05 | Проверка deinit и наличия символа | Отсутствующий обязательный символ — ERROR; недостижимый deinit требует отдельного сценария приложения |
| 10_02 | Проверка бесконечного цикла по инструкции | Оставить для специальных тестов конкретного ELF; не использовать как переносимый критерий |

Замеченные ловушки примеров:

- В 01_08 выражение `hadc2.Init.ContinuousConvMode = ENABLE` присваивает значение.
  Новый `fields` сравнивает отдельно полученные actual/expected, однако выражения
  GDB всё равно доверенные: API не является анализатором C и не запрещает все побочные эффекты.
- В 03_04 и некоторых других заголовках ID не соответствует имени файла.
  В текущем модуле ID требований и тестов сверяются автоматически.
- `except Exception` с единственным false теряет причину. Нужны FAIL/ERROR,
  traceback, значения и причина остановки.
- `return` уже убирает текущий кадр; следующий `finish` исполняет вызывающую функцию.
  Безусловное копирование цепочки `return; finish` меняет смысл теста.
- `b.n` и конкретный opcode зависят от генерации кода. Попадание в Error_Handler
  не доказывает отдельно отключение IRQ и бесконечность дальнейшего исполнения.

Семантика `return` и отличие от `finish` описаны в
[руководстве GDB](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Returning.html).
В архитектурном эскизе комментарий `force_return: return + finish` следует считать
устаревшим: текущий API выполняет только `return`.

## Каталог методов и границ

| Метод | Что подтверждает, сильная сторона | Ограничения и цена | Статус здесь |
| --- | --- | --- | --- |
| Чтение handle/аргументов HAL | Контракт вызова, выбор экземпляра, канала, режима; удобные имена | Handle — намерение ПО, не доказательство записи в MCU; locals могут исчезнуть при оптимизации | GPIO arguments проверен |
| Чтение RCC/GPIO после init | Итоговую цифровую конфигурацию | Не доказывает форму сигнала; сверять семантику чтения и маски в RM | RCC/GPIO проверены |
| Условный breakpoint | Нужный повторный вызов; минимум точек в тесте | Условие может проверяться хостом с остановкой при каждом попадании; влияет на время | Выбор второго TogglePin проверен |
| Следующая известная точка программы | Наблюдение эффекта после вызова без хрупкого номера строки | Между вызовом и точкой есть другой код; выбирать точку с однозначной причинностью | TogglePin → loop проверен |
| finish / FinishBreakpoint | Наблюдение возврата и его значения | Не применять вслепую после return, к ISR, inline/tail-call; валидировать кадр и событие | Общего API пока нет |
| Подмена аргумента/памяти | Ошибочные входы, границы, обработку внутри настоящего HAL | Только при понятных предусловиях; состояние искусственное, не физический отказ | NULL для обеих RCC-функций проверен |
| force_return | Ветку реакции вызывающего кода на HAL_ERROR/TIMEOUT/BUSY | Тело и эффекты HAL пропущены; правильный тип возврата зависит от ABI/debug info | RCC HAL_ERROR проверен |
| Hardware watchpoint | Доступ CPU к выбранной переменной/адресу | Ограниченные компараторы; нельзя считать универсальным наблюдателем записей DMA | Планируется |
| Буфер DMA после завершения | Результат передачи, длину, порядок, данные | Остановка CPU не гарантирует остановки DMA; нужен момент завершения и владение буфером | Планируется |
| IRQ/callback | Достижение обработчика, флаги, состояние ПО | Breakpoint искажает latency; несколько ожидающих IRQ могут изменить порядок | Планируется |
| Внутренний loopback/программный trigger | Часть цифрового пути без внешних проводов | Возможность зависит от конкретного периферийного блока; не покрывает внешний тракт | Планируется |
| Внешний генератор/loopback/анализатор | Входы, выходы, протокол и реальное время | Дополнительное оборудование, независимые измерения и синхронизация | Нет в текущем стенде |
| Trace/SWO/ETM | Поток событий при меньшем вмешательстве | Поддержка MCU, корпуса, выводов, отладчика, инструмента; не универсальная возможность | Не проверено |
| Host unit tests | Чистую логику, комбинации и граничные значения быстро | Не проверяет реальную периферию | Есть для инфраструктуры |

Условия GDB допускают побочные эффекты и функции. В тестах используем только
выражения без записи и вызова функций; после остановки `reach` повторно проверяет
условие, чтобы не принять остановку из-за ошибки его вычисления за успех.
[GDB: Break Conditions](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Conditions.html).

## Практический API и рецепты

Реализовано на Debug `-Og -g3`, GCC 13.3.1, GDB 14.2.90/Python 3.11.4:

```python
t.reach("HAL_GPIO_Init", when="GPIOx == GPIOC")
t.fields("*GPIO_Init", {"Pin": "GPIO_PIN_13", "Mode": "GPIO_MODE_OUTPUT_PP"})
t.reach("loop")
t.check("PC13 output", (t.value("GPIOC->MODER") >> 26) & 3, 1)
```

`fields` принимает целочисленные/указательные поля, ожидаемые числа либо C-выражения,
останавливается на первом несовпадении и сохраняет имя/actual/expected.
Float, массивы, допуски и сбор всех несовпадений пока не реализованы.
Макросы доступны в этом ELF благодаря `-g3`; при отсутствии макроса — ERROR,
а не подстановка нуля. Не надо выводить ожидаемое значение из того же actual.

```python
t.reach("HAL_RCC_ClockConfig")
t.set_value("RCC_ClkInitStruct", "0")
t.check("NULL injected", t.value("RCC_ClkInitStruct"), 0)
t.reach("Error_Handler")
```

В используемом Cube F4 V1.28.3 обе функции RCC явно возвращают HAL_ERROR при NULL.
`set_value` сохраняет before/after, `force_return` — имя функции и заданный возврат
в `mutations` JSON. После каждого теста reset/run восстанавливает штатное состояние.
Применимость к другим версиям HAL проверять по исходникам заново.

Рабочие рецепты находятся в [test_peripheral_methods.py](../profiles/f411ce/Tests/board/test_peripheral_methods.py).
Для ADC этот же шаблон может выбирать `hadc` + канал + ранг и проверять структуру
на входе HAL, но реальное преобразование требует отдельного источника/эталона.
Для SPI/UART проверка init должна дополняться передачей известных данных и проверкой
ошибок/таймаутов; чтение handle не заменяет эту часть. Для DMA сначала определить
момент окончания, ownership и при наличии cache — правила согласования памяти.

## Что нельзя заключить из остановок GDB

1. Нельзя получить достоверную latency/jitter непрерывно работающего приложения,
   регулярно останавливая CPU. HAL tick — программная шкала; не эталон частоты.
2. Нельзя доказать аналоговую точность ADC или качество фронтов GPIO/SPI по handle
   и регистрам. Нужен независимый физический стимул/измеритель.
3. Нельзя считать остановку ядра общей остановкой периферии. Для F411 изучать
   DBGMCU и freeze-настройки конкретных таймеров/watchdog в
   [RM0383, раздел Debug support](https://www.st.com/resource/en/reference_manual/rm0383-stm32f411xce-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).
   Политику freeze нужно фиксировать как условие опыта, не менять молча.
4. Нельзя переносить схему fault-регистров, число breakpoints и доступность trace
   между Cortex-M0/M4/M7/M33. Это свойства целевого MCU/ядра/доступа, а не общего Python API.
5. Нельзя гарантировать наблюдение удалённой компилятором переменной. Сначала
   проверить символы/места breakpoint и DWARF; для Release выбирать другие точки
   либо явно объявлять невозможность данного наблюдения.
6. Нельзя читать все MMIO «для диагностики»: встречаются read-to-clear, FIFO/data,
   зарезервированные адреса. SVD полезен, но требует сверки с RM и errata.
7. Нельзя вызвать несуществующую в ELF функцию deinit. Прямой `gdb call` существующей
   функции — другой эксперимент: он меняет контекст/стек, может ждать IRQ/тик или
   блокировку и не доказывает штатную достижимость пути приложения.

## Покрытие: несколько независимых измерений

Число зелёных тестов и совпадение ID требований не являются процентом покрытия кода.
Сейчас есть трассируемость заявленных требований, но нет счётчика statement/branch/MC/DC.
Разделяем следующие матрицы:

- Требования: перечисленные требования × позитивный сценарий × граничные случаи × ошибки.
- Периферия: init/config × работа × IRQ/DMA × ошибки/timeout × deinit/reinit × reset/recovery.
- Конфигурации: MCU/revision × HAL/version × compiler/optimization × probe/backend.
- Доказательство: контракт ПО × состояние регистров × результат выполнения × физическое измерение.

Для каждого незакрытого пункта записывать причину: нет сценария в приложении,
нет стимула/оборудования, нет наблюдаемости, ограничение MCU, тест ещё не написан.
Различать «не применимо» и «не проверено». Отсутствующий стенд/символ обязательного
сценария сейчас ERROR; в будущем SKIP должен иметь явную capability-причину.

Максимальное обоснованное покрытие достигается сочетанием host-проверок логики,
аппаратных проверок контрактов/регистров, управляемых инъекций и внешних измерений.
Структурное покрытие потребует отдельного способа измерения (инструментированная
сборка или поддерживаемая трассировка) с описанием его влияния на объект проверки.
Нельзя объявлять 100% branch coverage из факта попадания в несколько функций.

Текущее покрытие BlackPill:

| Область | Доказано тестами | Остаётся |
| --- | --- | --- |
| Boot | main → loop | startup fault/recovery, варианты reset |
| RCC | HSI/делители, HAL_ERROR и NULL в двух вызовах | timeout готовности, физическая точность частоты |
| GPIO | Аргументы init, регистры PC13, два переключения, выбор повторного вызова | Электрический уровень, другие режимы/пины, EXTI |
| Время | Изменение uwTick между проходами | IRQ latency, jitter, независимое измерение периода |
| ADC/SPI/UART/TIM/DMA | Не проверены этой прошивкой | Рабочий сценарий приложения и подходящий стимул |

## Журнал экспериментов

### E03: конфигурация после CubeMX-регенерации

Обновлены RCC-ожидания F411: HCLK 8 МГц, APB1 8 МГц, APB2 2 МГц.
Добавлены HW_ADC_DMA_INIT, HW_TIM2_INIT, HW_RTC_INIT: итог 14/14 CTest PASS.
F103 собирается с пользовательским IOC, но аппаратных утверждений по нему нет.

Практическая ловушка: в Cube F4 V1.28.3 (`stm32f4xx_hal_adc_ex.h`)
ADC_CHANNEL_TEMPSENSOR для F411 равен 0x10000012 — канал 18 плюс служебный бит HAL.
Первый вариант проверки SQR3 против этой константы дал FAIL (actual=18,
expected=268435474). Исправленная проверка сравнивает физический номер с 18,
ранг VREFINT — с 17. Нельзя механически переносить HAL-значения в MMIO-ожидания.

DMA пока проверяется по конфигурации handle, ADC — также по регистраторам рангов
и sampling time. TIM2 ещё остановлен. RTC проверяется по источнику/делителям,
не по времени alarm. Преобразование температуры, DMA callback, периодичность IRQ,
сон и пробуждение ещё не проверены. Общий User будет следующим этапом.

Каждая следующая запись должна содержать конфигурацию, метод, проверяемое утверждение,
позитивный и негативный контроль, результат, ограничения и ссылку на тест/отчёт.

### E01: контракт GPIO и выбор повторного вызова

BlackPill F411, ST-Link/OpenOCD 0.12, Debug GCC13, прошивка без изменений.
`HW_GPIO_ARGUMENTS` и `HW_GPIO_FILTERED_CALL` — PASS. Условие пропускает первый
TogglePin с ODR13=0 и выбирает следующий с ODR13=1; после вызова ODR13=0.
Неверное ожидаемое Mode=INPUT даёт FAIL с именем поля. Условие `0` даёт ERROR
по внешнему таймауту 2 с и host recovery; неизвестный аргумент даёт ERROR GDB.
Это подтверждает выбор вызова и цифровое состояние, но не качество сигнала.

### E02: естественный путь ошибки HAL

`HW_RCC_OSC_NULL` и `HW_RCC_CLOCK_NULL` — PASS с before/after в mutations.
Обе ветки выполняют проверку NULL в реальном HAL и достигают Error_Handler.
Для сравнения `HW_RCC_ERROR` принудительно возвращает ошибку без выполнения HAL.
Ни один сценарий не имитирует физическую неисправность HSI или аппаратный timeout.

Совместный прогон: 11/11 CTest (9 аппаратных и 2 host, один из них содержит 9 unit tests).
JSON/JUnit и SHA ELF находятся в `build/f411ce-debug-hwtest/hwtest`, отрицательные опыты —
`build/method-negative`. Артефакты локальные, в Git не включаются.

Отрицательные примеры сохранены в [profiles/f411ce/Tests/experiments](../profiles/f411ce/Tests/experiments/test_api_negative.py)
и намеренно исключены из обычного CTest. Повторение из корня проекта после сборки:

```powershell
New-Item -ItemType Directory -Force build/method-negative | Out-Null
$session = Get-Content build/f411ce-debug-hwtest/hwtest/session.json -Raw | ConvertFrom-Json
$session.tests = (Resolve-Path profiles/f411ce/Tests/experiments).Path
$session.out = Join-Path (Resolve-Path build/method-negative).Path 'runs'
$json = $session | ConvertTo-Json
$destination = Join-Path (Resolve-Path build/method-negative).Path 'session.json'
[IO.File]::WriteAllText($destination, $json, [Text.UTF8Encoding]::new($false))
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_BAD_FIELD
# Ожидается exit 1, FAIL, имя поля Mode.
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_FALSE_CONDITION --timeout 2
# Ожидается exit 2, ERROR, host recovery.
python -B hwtest/cli.py run --session build/method-negative/session.json --test HW_INVALID_CONDITION
# Ожидается exit 2, ERROR, неизвестный символ.
ctest --preset f411ce-hw -R '^hw.HW_BLINK$'
# После отрицательных контролей штатный тест должен пройти.
```

| Адаптеры серверов и контракты их готовности | Probe/serial/соединения и безопасное состояние выхода | Независимые ожидаемые результаты и границы покрытия |

Параметры Flash, DBGMCU identity, fault-handlers/регистры, breakpoint budget,
OpenOCD target и reset-команды теперь вынесены в profiles/<MCU>/target.toml.
F411 проверен, F103 пока описание без аппаратной валидации. Остаются предположения:
один непрерывный Flash-образ, Windows, расположение модуля в корне проекта и
reset/halt → reset/run. Разделение путей модуля и проекта-потребителя ещё впереди.
Состояние профилей и предложения для IOC: [PERIPHERAL_PLAN.md](PERIPHERAL_PLAN.md).

4. Проверить отдельный проект-потребитель внутри этого workspace, затем второе семейство
   при наличии оборудования. До этого заявлять поддержку только проверенного F411.
5. После подтверждения границ выделить пакет/репозиторий, версии конфигурации и API,
   пример подключения; добавить другие backends и CI по реальной необходимости.

Не включаем всё семейство STM32 посредством одной таблицы адресов: Cortex, Flash,
debug, безопасность и периферийные блоки требуют отдельных проверяемых возможностей.


## E04 — исполняемая периферия: DMA и IRQ (BlackPill)

Общее приложение `User` теперь выполняет рабочие измерения, а `Platform` задаёт
различающиеся HAL операции. Тестовых функций в прошивке нет. `app_state` — состояние
приложения: сырые измерения и счётчики событий. Это делает данные доступными через
DWARF без вызова целевых функций из GDB. Для готового чужого приложения потребуются
его собственные точки наблюдения, универсального имени состояния нет.

Проверено GCC13/Debug, F411, SWD без UART: 17 аппаратных сценариев PASS;
host traceability и 9 unittest также PASS. F103 собран, аппаратный перенос ожидается.
Первый общий CTest прогон: 18/19, из-за CP1251 в дополнении requirements.md;
после сохранения UTF-8 обе host-проверки прошли отдельно.

| Сценарий | Доказательство | Чего не доказывает |
| --- | --- | --- |
| ADC/DMA | Два completion callback, NDTR=0, две публикации; temperature raw 949/949, VREFINT 1509/1510 в первом прогоне | Точность °C/VDDA, все отказы DMA, отсутствие аналогового шума |
| TIM2 | Повторный callback правильного handle, счётчик +1, CEN=1 | Точный период 100 мс и отсутствие потерь IRQ |
| RTC | Два alarm A, счётчик 0→1→2, перевзвод из main | Точность LSI, смена суток, сохранение календаря после питания |
| Ошибка запуска ADC | force_return(HAL_ERROR) → Error_Handler, нет публикации | Реальную физическую причину отказа ADC |
| Потеря completion | Возврат из callback без публикации ready → Error_Handler по ожиданию с лимитом 100 мс SysTick | Зависание самого SysTick; здесь остаётся внешний таймаут GDB |

Плюс наблюдения callback: проверяется путь от реальной периферии через HAL к
приложению, без GDB inferior calls. Минус: остановки меняют поведение системы.
Политика этого опыта: не включаем DBGMCU freeze специально; периферия может идти
во время halt, а SysTick/CPU — нет. Поэтому сравниваем события и порядок публикации,
не длительность по часам хоста. Несколько обновлений TIM могут схлопнуться в один
pending IRQ. При проверке частоты нужны отдельный сценарий без промежуточных halt,
фиксация DBGMCU и внешний эталон/таймер захвата. Окно SVD также способно читать
регистры с побочными эффектами; аппаратные тесты выполнялись без отладочной UI-сессии.

ADC запускается в normal DMA на два halfword; после completion main останавливает
ADC/DMA, публикует данные и повторяет запуск. На F1 перед первым запуском выполняется
калибровка; на F411 такого HAL шага нет. Значения пока намеренно остаются raw:
фабричные калибровочные данные и допустимые погрешности F4 нельзя переносить на F1.

RTC alarm задаётся через 2 календарные секунды от прочитанного времени, дата F4
маскируется; следующий alarm ставится после обработки события в main. ISR только
считает события, не вызывает блокирующие HAL операции. Это событийная демонстрация,
не точный периодический планировщик: задержка main и фаза секунды меняют интервал.
Сгенерированная инициализация RTC сбрасывает время при каждом запуске приложения.

Следующий опыт — перенос на BluePill с отдельными регистрами/ожиданиями и профилем,
после согласованной замены платы. Затем: калиброванные величины, границы RTC,
Sleep/Stop, аппаратные ошибки и матрица покрытия. Число PASS не является покрытием кода.


## E05 — перенос на BluePill и отсутствующий RTC IRQ

На подключённой BluePill проверен device ID 0x410 до прошивки, GCC13 Debug,
Flash 11260 байт / RAM 1824 байта. Итог: 19/19 CTest,
то есть 17 аппаратных сценариев и две host-проверки. ADC raw во втором прогоне:
temperature 1758/1757, VREFINT 1495/1494. Это наблюдения, не точные °C/VDDA.

Перенос потребовал заменить GPIO MODER на CRH, AHB1ENR на APB2ENR, начальный
ODR13=0 на 1; ADC temperature channel 18 на 16, sampling 480 на 239.5;
DMA2 Stream0/NDTR на DMA1 Channel1/CNDTR; RTC PRER на PRLH/PRLL (39999).
Числовое значение ADC_SCAN_ENABLE также отличается. Контрактные тесты HAL и
сценарии ошибок удалось повторить с той же инфраструктурой GDB. Это подтверждает
переносимость механизма на эти две конфигурации, не поддержку всех STM32.

Первый прогон: 18/19. RTC callback отсутствовал в ELF, а ожидание завершилось
внешним таймаутом. В IOC RTC Alarm IRQ включён, но generated Core не содержит
ни handler, ни NVIC enable. Линкер удалил недостижимую цепочку HAL/callback,
несмотря на -g3. Исправление находится в пользовательском Platform F103:
IRQ вызывает HAL_RTC_AlarmIRQHandler, NVIC настраивается при setup. CubeMX-код
не менялся. При регенерации нужно проверить, не появился ли generated handler,
и убрать мост при дублировании. Два RTC alarm после исправления прошли.

Второй дефект: gdb.Breakpoint создал pending breakpoint даже после CLI
`set breakpoint pending off`. Target теперь проверяет bp.pending, удаляет его и
сразу возвращает ERROR с именем символа. Проверка на фактическом GDB 14.2.90
без платы подтверждает отказ и очистку; внешний таймаут остаётся страховкой.

Практический вывод: разделять проверки IOC, generated кода, ELF и аппаратного
поведения. Только последний уровень выявил отсутствие реального пути IRQ.
Настройка периферии не доказывает доставку события; callback в ELF не доказывает
работоспособность прерывания. Новые тесты пока отдельны для профилей, что делает
различия явными, но дублирует алгоритмы. Следующий шаг общего модуля — выделить
сценарии и отдельно проверяемые MCU-ожидания, сохранив идентификатор профиля в отчёте.

User отформатирован clang-format 23.1.1 по существующей конфигурации, без изменения
семантики. F411 после форматирования повторно собран; аппаратный прогон F411
не повторялся, так как стенд уже заменён на F103.


## E06 — общие сценарии и физические величины ADC

14 прежних сценариев перенесены в Tests/scenarios, три регистровые init-проверки
оставлены профилям. Общие алгоритмы получают явные MCU-ожидания; сборщик @case
и универсальная инфраструктура не изменены. Это устраняет дублирование исполнения,
но сохраняет отдельную регистрацию требований и специфичные условия аппаратуры.
Цена подхода — изменения общих сценариев требуют регрессии обоих MCU; F411 сейчас
собран и прошёл traceability, аппаратная регрессия ожидает замены платы.

Добавлены три общих ADC-сценария: реальные величины, недопустимые значения с
восстановлением, аналитические опорные точки. На BluePill 22/22 CTest PASS.
User теперь хранит VDDA/температуру и происхождение коэффициентов. Обе формулы
также проверены native-компиляцией исходного C++ (1/1 PASS), включая F411 interpolation
и повреждённую калибровку. Спецификация и источники: [ADC measurements](ADC_MEASUREMENTS.md).

Плюс чистой арифметики: граничные значения проверяются без платы и без зависимости
от HAL. Минус: native тест не доказывает чтение ROM, ADC sequencing, верность
калибровочных значений конкретного экземпляра и фактическую погрешность.
GDB-инъекции аргументов проверяют штатный путь публикации на MCU, но также обходят
физику датчика. Реальный ADC-тест отдельно подтверждает получение данных и лишь
широкий диапазон правдоподобия. Для метрологии нужны приборы и контролируемые условия.

Практический отрицательный опыт host-сборки: установленный MinGW не содержит
статическую libpthread; принудительная -static линковка не прошла. Обычная
динамическая линковка и runtime из PATH сработали; проект не меняет установленный
компилятор и глобальные пути. Native-проверка остаётся отдельным preset.


## E07 — правильный GPIO-тест не доказывает соответствие плате

Пользователь не наблюдал LED и предположил остановку MCU. При диагностике PC
находился в HAL_Delay, затем наблюдение без halt/reset показало running, рост
uwTick/adc_sequences и переключение PC13. Пользователь уточнил физический pinout
своей WeAct F103: LED находится на PB2. Это отличается от принятого ранее
предположения для BluePill. Точное состояние до первого подключения отладчика
не зафиксировано отдельным отчётом; диагностические действия сами влияют на MCU.

Исправлены IOC, два определения LED_USER и включение GPIOB clock. Generated Core
не форматировался и не регенерировался целиком: изменения ограничены тремя строками
для синхронизации новой конфигурации. Общие тесты больше не содержат GPIOC/PC13:
порт, маска пина и выражение уровня заданы отдельно для F103 и F411.

После прошивки: 22/22 CTest PASS. После закрытия GDB выполнено отдельное наблюдение
OpenOCD без halt/reset (9 чтений с паузами 200 мс). DHCSR=0x01010001, S_HALT=0,
S_SLEEP=0; состояние running до и после. adc_sequences вырос с 23 до 27,
uwTick — с 11483 до 13217. ODR GPIOB менялся 0x10↔0x14, IDR — 0xFFDB↔0xFFDF:
бит PB2 переключается как на выходе, так и во входном readback. Сессия закрыта
без остановки ядра. Это подтверждает исполнение и уровень пина в наблюдённом
интервале, но не яркость LED, его полярность, исправность или электрическую форму фронтов.

Отрицательный опыт: прежние PASS были корректны относительно неверного контракта
платы (PC13). Даже независимые от ELF ожидания могут повторять неверное исходное
предположение инженера. Поэтому матрица покрытия должна разделять:

- соответствие IOC/кода/регистров;
- выполнение и GPIO readback на MCU;
- физическое соответствие выводов ревизии платы и внешнюю наблюдаемость.

Признак «LED не мигает» сам по себе неоднозначен. Различать debug halt, аппаратный
Sleep/Stop, программный Error_Handler и ошибку разводки помогают DHCSR, PC, ход
счётчиков, ODR/IDR и схема/осмотр платы. Текущая прикладная прошивка Sleep/Stop
не вызывает. Успех reset_run в teardown — только факт выполнения команды;
для уверенности в автономной работе полезна отдельная проверка после отключения GDB.
Сам SWD/OpenOCD остаётся подключённым при чтении: это не проверка холодного старта
и не измерение потребления без отладчика.

После исправления пользователь визуально подтвердил мигание LED на PB2.
Таким образом, для этого экземпляра проверены и регистровое поведение, и связь с LED.


## E08 — обычный Sleep и независимое наблюдение без halt

Уточнены используемые экземпляры: WeAct BlackPill V3.1 (F411) и WeAct BluePill V1.1
(F103, проект производителя BluePill-Plus); ссылки находятся в README. Текущий стенд — F103.

User/app_idle заменяет активное ожидание LED: до истечения 500 мс HAL-времени
вызывается HAL_PWR_EnterSLEEPMode с WFI, SysTick остаётся включённым. Это обычный
Sleep (SLEEPDEEP=0), не Stop. Клоки периферии не перенастраиваются, SysTick будит
ядро примерно каждую миллисекунду; TIM2 и RTC также продолжают работать.
Инструкция WFI может завершиться сразу при уже ожидающем IRQ. Здесь не требуется
гарантировать сон на каждой итерации или исключить все прочие источники пробуждения.

Изучена реализация HAL PWR установленного Cube F1 V1.8.7: EnterSLEEPMode сбрасывает
SLEEPDEEP и выполняет WFI. При Sleep аргумент Regulator в F1 не используется.
Generated CubeMX и IOC на этом этапе не менялись; код приложения оформлен clang-format.

На BluePill 24/24 CTest PASS (22 аппаратных + 2 host). Новые сценарии отдельно
проверяют WFI-параметр, SysTick handler, обычный режим сна и возврат к loop;
с временным отключением SysTick interrupt наблюдают TIM2 callback, восстанавливают
SysTick и проверяют продолжение работы. RTC при этом активен: тест не доказывает,
что только TIM2 мог пробудить ядро, и остановка на HAL entry сама по себе ещё не
доказывает выполнение WFI. Прежние GPIO/ADC/DMA/RTC/error-path тесты также прошли.

Поэтому добавлен отдельный tools/observe_sleep.py: после закрытия GDB, без новых
halt/reset, он читает через OpenOCD DHCSR, SCR, uwTick и DBGMCU_CR. В первом опыте
30/30 выборок имели S_SLEEP=1, ни одна не имела S_HALT; SLEEPDEEP=0,
uwTick продвинулся на 1324. Это выборочное наблюдение реального состояния ядра,
а не частота/длительность сна. Пауза 37 мс не устраняет все эффекты синхронизации,
и число sleep_samples нельзя выдавать за процент энергосбережения.

Отрицательный контроль: ядро намеренно остановлено отдельной командой halt.
Наблюдатель вернул FAIL (S_HALT и отсутствие продвижения времени). После resume
повторная проверка дала PASS: 28/30 sleep samples, uwTick +1331. Плата оставлена
работающей, LED продолжает обслуживаться приложением.

Существенное ограничение: наблюдён DBGMCU_CR=0x307, то есть debug-настройки активны,
включая DBG_SLEEP. Наблюдатель не записывает эти биты и сохраняет значения в отчёте.
SWD/debug могут удерживать тактирование, поэтому эти результаты не подтверждают
паспортный ток Sleep. Для потребления нужен внешний измеритель и запуск без
отладчика. Также нужен отдельный контроль холодного старта после снятия питания.

F411 после изменения собран, но аппаратно новый ADC/Sleep набор ещё не проверен.
Stop остаётся следующим отдельным опытом: определить RTC/EXTI wake source,
сохранение времени при остановке SysTick, восстановление RCC и влияние DBG_STOP.

## Runtime-совместимость на BluePill

В отчёты добавлен compatibility schema 1: фактические GDB/Python, OpenOCD и
firmware/API ST-Link. Прогон BluePill: 22 HW + 2 host PASS; внутри host.hwtest
12 unit tests, включая неизвестный формат баннера и отсутствующий GDB API.
Версии запуска: GDB 14.2.90.20240526-git / Python 3.11.4, OpenOCD 0.12.0,
ST-Link V2J43M28 / API 2. У всех 22 HW-отчётов проверены metadata и reset_run.

Отказный опыт в настоящем GDB: в список обязательных API добавлено заведомо
отсутствующее имя; агент сохранил ERROR, хеш ELF и connection_attempted=false.
Соединение с MCU не запрашивалось. При валидированном отчёте с этим признаком
host не выполняет recovery reset; при неизвестном результате сохраняет recovery.
Наличие API ещё не доказывает его семантику: реальные breakpoint/IRQ/инъекции
по-прежнему проверяются аппаратными сценариями. Эти проверки не измеряют покрытие.

Плюс: версии привязаны к конкретному запуску, а не выводятся из названия GCC.
Ограничения: парсер баннеров может не распознать иной backend/отладчик (null с
причиной); исходники библиотек и compiler flags ещё не связаны с ELF build-time
manifest. Изменение аппаратного сценария или прошивки для этой функции не нужно.


## Один набор сценариев с разными GDB-серверами

На BluePill одинаковые 22 HW + 2 host CTest прошли через OpenOCD 0.12.0 и
ST-LINK GDB Server 7.14.0. Прошивка и ожидания тестов не менялись. Общий RSP/GDB
слой переносим для этих сценариев; monitor/reset/finish вынесены в backend.
Проверена запись O0-образа через ST и возврат к штатному Og-образу, verify-only
отказ, timeout и recovery. Отдельно после ST reset+detach наблюдение OpenOCD
без halt/reset показало 30/30 Sleep samples и uwTick +1435, S_HALT не установлен.
Это подтверждает работающий MCU после завершения ST-сессии; не измеряет ток.

Плюс: прямой доступ к инфраструктуре CubeProgrammer без переписывания сценариев.
Минусы: зависимость от установленного ST toolchain, собственные команды reset,
баннеры/порты и иной способ чтения работающего MCU. Даже команда monitor с ответом
OK не всегда доказывает выполнение операции: UM2576 отмечает неподдерживаемые
ReadDP/WriteAP/WriteDP, которые возвращают OK. Для новых возможностей проверять
реальный эффект, а не только код возврата. J-Link проверен следующим отдельным этапом.
Инструкция, матрица и границы доказательства: [GDB_BACKENDS](GDB_BACKENDS.md).


## J-Link: общий RSP и отдельное наблюдение Commander

На том же BluePill 24/24 CTest прошли через J-Link V8.32, без изменений User и
ожиданий периферии. Flash breakpoints отключены явно; используются аппаратные

После завершения сервера Commander читал DHCSR и адрес uwTick из ELF: 10/10
Sleep, S_HALT=0, tick +350 ms. Запрашивались только connect/read/sleep/q, но
влияние init/connect отладчика этим не исключено. Это хороший отдельный способ
проверить завершение GDB-сессии; не основание заявлять измерение потребления или
универсальную поддержку чтения периферии на ходу. Наблюдение пока не включено
в общий runner. Детали, ошибки исходных shell-примеров и команды: [JLINK](JLINK.md).


## Привязка сведений о сборке к аппаратному результату

На BluePill F103 + J-Link / J-Link GDB Server V8.32 проверен post-link manifest
schema 1. Чистая сборка GCC 13.3.1 и 24/24 CTest прошли (22 HW, 2 host;
внутри host.hwtest — 23 unittest). Все 22 аппаратных отчёта содержат одинаковый
снимок сборки, совпадающий ELF SHA, image_verified и teardown=reset_run.
Прошивка сохранила размер FLASH 12376/RAM 1840 байт и прежний SHA-256 ELF.

Положительный опыт: manifest различает CubeFW 1.8.7, HAL 1.1.10,
CMSIS Device 4.3.5 и Core 5.1; полный номер Cube не подменяет версию HAL.
Удаление manifest привело к его восстановлению через обычный build; результат
побайтно совпал. Повторный build не перелинковывает образ. Отчёт использует
сохранённый снимок и не перечитывает текущие библиотеки во время HW-run.

Отрицательный опыт: копия manifest с подменённым ELF SHA дала ERROR в настоящем
раннере до objcopy/GDB/server; server.log не создан, подключения к MCU не было.
Host-тесты отдельно проверяют несовпадение профиля, отсутствие файла/схему,
пустые данные и запрет старта subprocess при ошибке привязки.
Ninja выдаёт для startup `.s` VALID с нулём зависимостей: понадобился отдельный
путь для plain assembler; включения файлов в таком пути пока запрещены.

Влияние на стенд: сама проверка manifest аппаратуры не касается; дальнейшие
сценарии сохраняют прежние halt/reset/injection эффекты. Завершение HW-набора
возвращает MCU к выполнению. Этот этап не расширяет покрытие периферии.

Ограничения: post-link снимок требует надёжных timestamps, неизменного toolchain
и отсутствия параллельного редактирования. Он не является аттестацией, проверкой
семантики HAL или доказательством соответствия IOC сгенерированному коду.
Linker/runtime libraries, effective macros и версия Python-адаптера ещё не
покрыты; детали в [COMPATIBILITY](COMPATIBILITY.md). Следующий шаг — явные
проверки HAL-контрактов до инъекций, на том же F103/J-Link стенде.


## Выборочный ELF/HAL preflight перед инъекциями

F103/J-Link: добавлены семь контрактов, проверяемых отдельным GDB без target connect
до запуска сервера. Успешная проверка сигнатур/полей/enum дополняет, но не заменяет
аппаратные GPIO/RCC/ADC сценарии; полный CTest — 24/24 PASS. Неверный символ,
return type, arity, имя аргумента, тип поля и enum дали ожидаемые ERROR offline.
Настоящий раннер подтвердил отказ без сервера при неверной сигнатуре; неизвестный
reviewed-source hash RCC остановил его ещё до GDB. Положительное доказательство
семантики NULL остаётся сочетанием ручного анализа конкретного HAL и HW-сценария.

Выявлен ложный отрицательный результат глобального поиска одноимённых C/C++ типов.
Решение — разрешать тип в блоке нужной функции, а порядок аргументов хранить списком.
Версия GDB или строковое имя типа не заменяют этого контекста. Отладочные типы
доступны без запуска MCU, но доступность значения аргумента в момент инъекции
всё равно требует проверки после остановки. Политика reviewed-source hash
консервативна: даже редакционное изменение исходника требует повторного анализа;
зато изменение HAL без смены строки версии не проходит незамеченным.

Сам preflight не влияет на MCU; последующие HW-сценарии сохраняют прежние эффекты
halt/reset/injection. Система не обещает универсальную совместимость HAL: 15 других
сценариев имеют NOT_REQUESTED, F411/H503 ещё не адаптированы, effective macros и
все транзитивные зависимости не проверяются на семантику. Подробности и команда
воспроизведения: [HAL_CONTRACTS](HAL_CONTRACTS.md).


## F411: HAL-контракты и два сервера ST-Link (2026-09-24)

Стенды подтверждены владельцем одновременно: BlackPill F411 + ST-Link и BluePill
F103 + J-Link. Аппаратные действия этого этапа выполнялись только на BlackPill;
F103 использовался для offline-регрессии контрактов по сохранённому ELF.

F411 собран начисто GCC 13.3.1: Flash 12220, RAM 1904 байт, Cube F4 1.28.3,
HAL 1.8.5, CMSIS Device 2.6.11/Core 5.6. Manifest содержит 29 объектов/89 входов.
SHA-256 ELF: `2b7a1e9da167fe613af6e9f3246ed78be567528cd4b974056093b05c025747b6`.
OpenOCD 0.12.0 и ST GDB Server 7.14.0 дали по 24/24 CTest на этом же ELF:
22 HW + 2 host, включая ADC calibration vectors, invalid/recovery и Sleep.
Все HW-отчёты подтвердили Flash и reset_run; семь контрактов PASS, остальные
пятнадцать NOT_REQUESTED. OpenOCD записал обновлённый образ один раз;
ST затем прочитал и подтвердил тот же образ без повторной записи.

Перенос выявил различие RCC API: указатели F4 const, F1 — без const. Добавлена
проверка const адресуемого типа, отдельный reviewed-source hash F4. На обоих ELF
прошли 80 положительных проверок и семь отрицательных вариантов, включая неверный
const. Одинаковая бизнес-логика не означала побайтово одинаковую декларацию HAL.

ADC в двух прогонах: 3304/3302 мВ, 27232/27352 м°C, quality=FACTORY. Это значения
конкретных измерений и проверка пересчёта, не доказательство точности температуры
или VDDA. Эталонное сравнение и энергопотребление не измерялись. Sleep-проверки
с halt подтверждают пути выполнения и IRQ, но не заменяют наблюдение S_SLEEP без halt.

Отказный опыт: внешний timeout 1 с для RTC через каждый backend дал ERROR,
затем host recovery выполнил reset_run; следующий HW_BOOT прошёл. Финальное
завершение оставило F411 работающим. Политика reset_run относится к этому приложению.
Запись через ST, отрицательный verify-only и неожиданное отключение USB на F411
в этом этапе не проверялись — результаты таких опытов на F103 не переносим.

Первый набор не подключился: старый local TOML содержал serial другого ST-Link.
Причина сохранена в server.log, тесты получили инфраструктурный ERROR. CubeProgrammer
показал единственный подключённый ST-Link; по подтверждённой владельцем разводке
обновлены только игнорируемые локальные TOML. Наличие USB само по себе не считалось
доказательством правильной платы. После исправления выполнены полные наборы заново.

Локальные отчёты сравнения и recovery: `build/f411ce-backend-comparison/`;
offline результаты разделены по профилю в `build/contract-validation/`.
Логи и серийные номера не включаются в Git. Следующие непроверенные сочетания:
F411/J-Link и регрессия новых механизмов F103/ST-Link; смену проводки согласовывать.

## Эксперимент при расхождении маркировки и DEV_ID

[F401_MARKING_EXPERIMENT](F401_MARKING_EXPERIMENT.md): явно разрешённый запуск
F401CC на DEV_ID0x431 с неизменённым ELF. Override хранится отдельно от исходного
профиля и включается в отчёт; результаты относятся только к экземпляру.
Init-проверки регистров прошли, но runtime не достигнут из-за двойного setup.
Это пример того, что PASS конфигурации ADC не доказывает физический источник
канала или работу DMA. Таймаут скрыл стек в основном отчёте; отдельный halt/bt
после recovery установил Error_Handler при повторном запуске TIM2. Halt меняет
выполнение, а reset/run не устраняет логическую ошибку приложения.

После исправления дублей на том же экземпляре получено 22/22 HW PASS (248 проверок),
включая ADC runtime с channel16 и правдоподобными 3,289 В/27,1 °C; live Sleep PASS.
Смена результата при изменении только двух повторных вызовов подтверждает причину
первого сбоя. Это основание доверять проверенным функциям на экземпляре, но не
объявлять DEV_ID ошибочным или подлинность MCU установленной. Сохранять исходный
и исправленный ELF SHA отдельно; число проверок не является покрытием кода.

## Общая политика DEV_ID после эксперимента

Отдельный override заменён штатной warn/strict политикой. F401CC через OpenOCD
и ST server прошёл 24/24 CTest; каждый HW-отчёт сохраняет ожидаемый и наблюдаемый
DEV_ID и Flash size. Strict подтверждён отказом до записи. Это позволяет исследовать
плату по маркировке, не скрывая противоречащую ей информацию. Риски интерпретации
регистров другого MCU и границы доказательства: [TARGET_IDENTITY](TARGET_IDENTITY.md).
После ST detach live Sleep PASS: 30/30 выборок, tick+1360ms, ядро не в halt.

На F103C8/J-Link выявлено другое сочетание: DEV_ID0x410 совпадает, регистр Flash
показывает128 KiB при выбранных64 KiB. 24/24 CTest и strict boot PASS с предупреждением
размера. Это подтверждает необходимость разделять identity и ёмкость; ни имя MCU
из программы, ни успешная проверка малого образа не доказывают работоспособность
всей памяти. Верхние64 KiB не использовались. См. [TARGET_IDENTITY](TARGET_IDENTITY.md).
