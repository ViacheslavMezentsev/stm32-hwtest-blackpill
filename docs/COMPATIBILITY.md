# Совместимость тестовой системы STM32

Общее API управления GDB не означает одинакового HAL API или одинаковой периферии.
Совместимость относится к конкретной проверенной комбинации платы, MCU, прошивки,
Cube/HAL/CMSIS, компилятора, GDB/Python, сервера и отладчика.

## Что реализовано и что планируется

Сейчас работают профили f103c8/f411ce: target.toml schema 1, отдельные expectations,
общие проектные сценарии, проверка MCU перед Flash, проверка образа, лимит breakpoint,
запрет pending breakpoint, внешний timeout. Отчёт сохраняет профиль, хеш ELF/образа,
версии GDB и встроенного Python. Добавлен блок `compatibility` schema 1:
версия host Python, фактические GDB/Python, OpenOCD, ST либо J-Link GDB Server и firmware/API ST-Link из
журнала текущего запуска (ST не сообщает API version: null). Перед подключением
к серверу из GDB проверяется наличие используемых
GDB API; отсутствие обязательного API даёт ERROR до reset/Flash. Это проверка
наличия, а не доказательство семантики или исправности аппаратуры.
Build manifest schema 1 сохраняет сведения о сборке и проверяется до запуска сервера.
Для семи сценариев каждого профиля F103/F411 реализован ELF/HAL preflight до запуска сервера:
сигнатуры, аргументы, поля, enum и выбранные reviewed-source hashes.
[Механизм и ограничения](HAL_CONTRACTS.md). Capability registry и полная проверка
семантики HAL не реализованы; дальнейшие требования ниже остаются планом. H503 отложен.

## Границы слоёв

| Слой | Стабильный смысл | Что зависит от окружения |
| --- | --- | --- |
| hwtest / GDB adapter | Достичь точки, прочитать значение, проверить условие, записать инъекцию, оформить результат | Наличие Python API, pending/stop events, lazy/optimized values, ABI и восстановление кадра |
| Backend отладчика | Подключение, reset, Flash verify, bounded cleanup | Сервер/версия/драйвер/прошивка отладчика, transport, команды monitor, доступ в low-power |
| MCU/HAL adapter | Смысл операции «ADC sequence completed», «timer IRQ», «RTC alarm» | Сигнатуры HAL, handle/поле/enum, регистры, callback registration, прерывания, калибровка |
| Профиль платы | Соответствие физическим выводам и стенду | LED, кварцы, питание, внешние соединения, реальные возможности конкретного корпуса |
| Проектный сценарий | Требование, стимул, независимое ожидание, наблюдение | app_state и функции приложения, доступные пути исполнения и конфигурация IOC |

Функции `reach`, `fields`, `set_value`, `force_return` остаются небольшими примитивами.
Они не должны автоматически выбирать «похожую» HAL-функцию по имени и скрывать различия.
Приложение-специфичные сценарии остаются вне универсального hwtest. Адаптер можно
делить между профилями только при совпадении проверенного контракта, а не названия семейства.

## Что записывать в воспроизводимый запуск (план)

- Плата и ревизия, полный part number, revision/device ID, источник pinout, размер памяти.
- Коммит проекта и фреймворка, выбранный профиль, хеш IOC и ELF/Flash-образа.
- Версия Cube-пакета отдельно от версий HAL и CMSIS Device/Core; используемые MCU define,
  HAL configuration и callback-registration macros. Локально изменённые библиотеки —
  также по ревизии/хешу исходников, строка версии сама по себе недостаточна.
- Компилятор/ABI/FPU flags, оптимизация/LTO, debug format и -g3.
- Фактические GDB/Python и доступные API, версия сервера, прошивка отладчика,
  схема reset, доступность точек, debug freeze/low-power policy.
- Версия адаптера, выполненные проверки возможностей и причины невыполненных сценариев.

Не публиковать персональные пути и серийные номера отладчиков. Новые поля вводить
через явную версию схемы, тесты чтения/ошибок и snapshot в отчёте. Текущий строгий
загрузчик target.toml не принимает произвольные новые поля — не обходить его молча.

## Предварительные проверки перед запуском сценария (план)

1. На host выбрать явный набор требований для профиля, сверить источники/версии,
   metadata тестов и доступный backend. Не импортировать GDB-код при AST-сборе.
2. В GDB проверить наличие используемых API через доступность операций; номер GCC
   не определяет версию GDB/Python. Сохранить main-thread правило и внешний timeout.
3. Проверить ELF: нужные символы, типы и поля, возможность прочитать макрос/константу,
   отсутствие optimized-out/pending. Макрос может зависеть от compilation unit;
   установить нужный контекст или использовать обоснованное независимое ожидание.
4. Проверить HAL-контракт: сигнатуру/семантику функций, предусловия, callback путь,
   обработку ошибок и timeout source. Сначала без мутаций, затем разрешённые инъекции.
5. Проверить MCU identity/доступ/образ до выполнения сценария. Матрица совместимости
   должна различать сборку, проверку контракта и положительный аппаратный результат.

Не считать `-g3` гарантией присутствия функций или макросов в ELF. Макрос может
быть выражением/маркером, а не значением регистра: уже обнаружен flagged constant
температурного канала F411. Сравнение handle с HAL enum полезно для контракта,
но проверка физической настройки требует независимого чтения регистров по RM.

## Инъекции и результаты

`force_return(HAL_ERROR)` проверяет реакцию вызывающего кода, но пропускает тело
HAL и его побочные эффекты. Перед NULL-инъекцией проверить именно используемую
версию HAL: NULL может обрабатываться, разыменовываться или запрещаться assert.
Статический/inline API, LTO и изменённая сигнатура могут требовать другой точки
наблюдения — отсутствие старого символа не является аппаратным отказом MCU.

Обязательный контракт отсутствует → ERROR до запуска соответствующего сценария.
Ожидание поведения не выполнено при совместимом контракте → FAIL. Неподдерживаемая
возможность заранее отмечается как не проверенная/не применимая в плане профиля,
с причиной; её нельзя считать PASS или молча исключать ради зелёного отчёта.
Будущий NOT_APPLICABLE/SKIP потребует отдельного изменения протокола/traceability;
текущий раннер использует PASS/FAIL/ERROR и не имеет такой реализации.

## Уже проверенные примеры различий

| Различие | Практическое следствие |

| LL CubeH5 V1.7.0 задаёт TEMPSENSOR_CAL1_TEMP=30 и CAL2_TEMP=130; F411 использует 30/110 | adc_convert_factory сейчас специфичен F411; до H503 сделать параметры/векторы явными |

## Приёмка нового семейства

Наличие CMake family target, SVD или успешный build — только отдельные предпосылки.
Для признания поддержки нужны: конкретный manifest, проверка API/контрактов,
аппаратные положительные и отрицательные сценарии, восстановление стенда после
ошибки и перечень непроверенного. Обновление HAL/GDB/backend запускает подходящую
регрессию; сохранённые старые PASS не переносятся на новую комбинацию автоматически.
Следующий кандидат — h503cb, этапы и периферия в [PERIPHERAL_PLAN](PERIPHERAL_PLAN.md).

## Runtime manifest schema 1

Блок `compatibility` добавляется в result.json и JUnit system-out для PASS/FAIL/ERROR,
включая отказ до запуска сервера. Старые верхнеуровневые gdb_version/python_version
сохранены. Источники обозначены в evidence; недоступные значения — null и причина,
а не предполагаемая версия. Из server.log извлекаются только токены версии,
firmware/API; строки целиком, пути и серийный номер в этот блок не копируются.
Это не очистка остальных диагностических логов от локальных данных.

`scope=runtime-only` относится к блоку `compatibility`; сведения о сборке находятся
в отдельном `build_manifest`. `compatibility.build.provenance` указывает, прошёл ли
этот manifest проверку привязки к ELF и target.toml. Старые session.json без пути
manifest поддерживаются с явным unavailable; новые сессии CMake требуют manifest.
Неизвестный формат баннера оставляет метаданные недоступными и сам по себе не
меняет результат сценария. Несовместимый обязательный GDB API — инфраструктурный ERROR.

ST backend проверен на BluePill; команды finish/reset сохраняются в backend_commands.
Сам ST-сервер подключается к SWD при запуске до GDB preflight. Подробнее:
[GDB_BACKENDS](GDB_BACKENDS.md). Новый offline ELF/HAL preflight выполняется до сервера; проверен на F103/J-Link и F411/ST-Link (OpenOCD и ST server).

J-Link V8.32 проверен на F103: отдельные setup/reset/finish, Flash breakpoints
отключены. Фактическая версия firmware J-Link сохраняется отдельно от пакета;
API version ST-Link к J-Link неприменима. [Результаты](JLINK.md).

## Build manifest schema 1

При линковке HWTEST-target создаётся `build/<preset>/hwtest/build-manifest.json`.
Реализация рассчитана на Windows, Ninja и один firmware-target. CMake включает
compile_commands; POST_BUILD читает базу `ninja -t deps`, проверяет VALID и время
изменения входов относительно объекта. Для plain `.s` с пустыми зависимостями
учитывается сам файл; `.include`, `.incbin` и `#include` требуют расширения механизма
и сейчас отклоняются. Изменение скрипта manifest, target.toml, YAML или IOC вызывает
перелинковку. Отсутствующий byproduct также восстанавливается сборкой.

Содержимое:

- SHA-256 ELF и target.toml; хеши объектов и использованных C/C++ исходников/заголовков,
  startup, IOC, YAML и профильного FLASH linker script;
- имя, хеш и версия compiler executable; выбранные флаги define/ABI/оптимизации/debug,
  хеш полной команды без публикации её персональных путей;
- название CubeFW-пакета отдельно от числовых деклараций HAL и CMSIS Device/Core
  с файлом-источником и его хешем. Это чтение литералов, не выполнение препроцессора.

Раннер сначала копирует ELF, сверяет его SHA-256 и текущий target.toml с manifest.
Несовпадение, отсутствующий файл или неподдержанная схема дают ERROR до objcopy,
GDB и сервера. Принятый manifest копируется в каталог запуска и result.json/JUnit.
Исходники и установленный CubeFW во время аппаратного теста не перечитываются:
отчёт описывает сохранённую сборку, даже если рабочие исходники после неё изменились.
Для новых сессий сначала выполнить configure/build, затем тестирование.

Границы доказательства: это снимок после линковки, а не аттестация происхождения
бинарника. Требуются надёжные timestamps, отсутствие параллельного редактирования
и неизменная установка компилятора между компиляцией и снимком. После замены
компилятора нужна чистая пересборка в отдельном build. Не сохраняются все linker
flags и содержимое предсобранных runtime-библиотек; хеш команды не заменяет их.
Не вычисляются эффективные условные макросы HAL/callback-registration. Хеш IOC
фиксирует файл рядом со сборкой, но не доказывает соответствие ему генерации CubeMX.
Проверка SHA не является цифровой подписью. Полные личные пути не записываются
в manifest; остальные диагностические логи по-прежнему могут содержать их.

Приёмка F103: CubeFW 1.8.7, HAL 1.1.10, CMSIS Device 4.3.5, CMSIS Core 5.1;
31 объект, 123 входа. Расширение HAL-контрактов, версия Python-адаптера и effective macros
остаются следующими этапами; наличие декларации версии не доказывает совместимость API.

F411: Cube F4 1.28.3 / HAL 1.8.5 / CMSIS Device 2.6.11 / Core 5.6; RCC принимает const-указатели. Профиль адаптирован явно, отрицательная проверка квалификатора выполнена на F1/F4. Детали в [HAL_CONTRACTS](HAL_CONTRACTS.md).
