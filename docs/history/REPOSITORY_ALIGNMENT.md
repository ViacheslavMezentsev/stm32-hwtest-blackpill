## Общая структура

| Каталог | Назначение в обоих примерах | Перенос в BlackPill |
| --- | --- | --- |
| src/ | Код приложения и адаптер платы | User и собственный CMSIS platform; разделить общую логику и MCU-specific код |
| cmsis/ | Неизменённые сторонние CMSIS файлы | Минимальный набор F4 с версией, происхождением и лицензиями; не форматировать |
| ld/ | Скрипты компоновщика | F401:256 КиБ Flash/64 КиБ RAM; F411:512/128 КиБ; не увеличивать по DEV_ID |
| cmake/ | Toolchain, выбор платы и интеграция HIL | Тонкий самостоятельный CMake, отдельные build на MCU/toolchain |
| hil/profiles/ | Описание MCU для GDB | f401cc/f411ce; точные размеры, identity, диагностика |
| hil/tests/ | Сценарии, требования, contracts | Общие сценарии с профильными ожиданиями; HAL cases принадлежат fixture модуля |
| hil/stands/ | Примеры подключения | Только example TOML; serial/личные пути в игнорируемых local/remote TOML |
| modules/ | Закреплённый stm32-gdbtest | Удалить ненужные build-подмодули только после замены сборки |
| .vscode/ | Сборка, отладка, SVD | Согласовать с presets и обоими MCU |
| .github/ | CI сборки и offline | Два MCU, отдельное доказательство host/prepare; HW только на согласованном стенде |
| docs/ | Подробности и история | Архитектура, методика, протоколы и исторические опыты остаются доступны |

emu/ добавляется только вместе с проверенной моделью/сценарием. Renode-модель
F103 и её результаты нельзя переносить на F4 как доказательство. Пустой каталог
ради внешнего сходства не нужен. UART/VCOM не становится обязательным:
сейчас подтверждена только SWD-проводка.

## Профили и поведение

F411CE и F401CC — два варианта общей прошивки, а не копии Core/User.
PC13 active-low общий; канал температурного датчика, калибровка, память,
startup/IRQ и clocks задаются для конкретного MCU. Исторические DEV_ID
несовпадения F401 сохраняются как предупреждение в рамках принятой политики;
успешный тест F411 не подтверждает F401.

Presets должны одинаково выражать Debug, Release и HIL для каждого MCU,
как в BluePill. Точные новые имена и таблицу замены старых f411ce-*/f401cc-*
зафиксировать в пакете реализации; не ломать VS Code и CI неявным переименованием.
Новый собственный код размещать в lowercase каталогах; имена стороннего CMSIS
сохраняются. При переносе правила форматирования User перенести на собственный src.

Основное приложение сохраняет измерения ADC/DMA, TIM, RTC и Sleep, пока
изменение поведения не описано явно. BluePill POST/UART не является требованием
к BlackPill. В частности, RTC приложения перепланирует событие через две секунды;
маскированный ежесекундный Alarm fixture модуля не является идентичной заменой.

## Пользовательское описание

README.md и README.en.md: назначение и DDTT без тестовых hooks, две платы,
требования, clone/build, таблица presets, запуск HIL, ограничения, структура,
лицензии и ссылки. Человек должен понимать сценарий использования с первого абзаца.
История измерений и точные результаты — STATUS и протоколы, не журнал в README.
CHANGELOG также вести RU/EN после перестройки; инструкции агента отражают реальную
структуру. Общая документация механизма ссылается на закреплённый stm32-gdbtest.

## Приёмка и удаление старых копий

1. Принять интеграцию0f8a358, затем этот зависимый план после собственного CI.
2. Одним крупным пакетом подготовить CMSIS-приложение, два профиля, presets,
   HIL, документацию RU/EN и VS Code. Сборка/prepare обеих плат на Windows/Linux.
3. Проверить F411CE + ST-Link/OpenOCD, затем запросить смену платы на F401CC.
   На каждом MCU выполнить основной набор, инъекции, recovery и согласованное
   финальное состояние прошивки. Не переносить старые HAL PASS на новый CMSIS код.
4. После приёмки убрать активные F030/F103/F429 и лишние build-зависимости;
   оставить ссылки на принятые fixtures/результаты модуля. H503 приостановлен,
   К1921/errata и их документы инвентаризировать отдельно; не удалять их как
   якобы заменённые STM32-примерами. Историю и исходную архитектуру сохранить.
5. Сверить ссылки и CI обоих профилей; затем сопровождение и оптимизация тестов.

Общая матрица MCU/backend и развитие тестового механизма остаются в stm32-gdbtest;
здесь проверяется самостоятельный BlackPill-потребитель с двумя профилями.
