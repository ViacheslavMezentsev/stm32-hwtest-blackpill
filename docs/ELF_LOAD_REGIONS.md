# Возврат на STM32 и проверка ELF load sections

Дата: 2026-09-24. Опыты К1921ВГ015 завершены, владелец разобрал тот стенд.
Подтверждены два текущих подключения: F411CE + ST-Link/SWD и F103C8 + J-Link/SWD.
К1921 в этом этапе аппаратно не использовался.

## Изменение

В отдельном stm32-gdbtest исправлено сплошное сравнение BIN: агент сравнивает
только загружаемые секции ELF по LMA. `.data` проверяется по месту начального
образа во Flash; `.bss` и debug sections не сравниваются. Промежутки в BIN
заполняются 0xFF, но их содержимое на MCU не предполагается и не проверяется.
Подробный контракт и план полного образа/CRC принадлежат
[модулю: IMAGES](../modules/stm32-gdbtest/docs/IMAGES.md).

Обязательные проверки до сервера: корректный список, отсутствие перекрытий,
Flash-границы профиля и совпадение диапазона BIN. После подключения сохранён
контроль factory capacity. При readback различаются несовпадение байтов и ошибка
чтения; чтения ограничены блоками 4096 байт. Отчёт явно показывает
`scope=elf-load-sections`, `gaps_verified=false`, `full_region_crc_verified=false`.

## Проверки

| Проверка | Результат |
| --- | --- |
| Host ядра, включая девять новых регрессий | 53/53 |
| F411CE / ST-Link / OpenOCD | 22/22 аппаратных сценария |
| F103C8 / J-Link GDB Server | 22/22 аппаратных сценария |
| Повтор host из закреплённого подмодуля | 53/53 |
| Штатный CTest HW_BOOT после обновления gitlink | PASS на обоих стендах |
| Offline разбор сохранённого К1921 ELF | 5 секций, 3728 байт payload, диапазон 3744 байта |

Обе STM32 прошивки оставлены reset/run. Отладчики/проводку менять не нужно.
Изменений прикладного firmware и CubeMX нет. Host-тесты проверяют различающиеся
байты в незагруженном gap, повреждение payload, RAM VMA/Flash LMA, неверные границы,
перекрытия, неполное чтение, malformed objdump и отказ до запуска GDB/server.

Штатные STM32 ELF в этом прогоне непрерывны: семь load sections, соответственно
12220 и 12376 байт. Физический опыт с намеренным gap на этих платах не выполнялся;
его модель покрыта host-тестом, исходное аппаратное наблюдение — в
[протоколе К1921](K1921VG015_POC.md). Это различие важно для границ доказательства.

ELF SHA256:

- F411CE: `dedd1d59c9fadd1ce32c715016260344eb2b33da5c1f92ee14032810672b3009`.
- F103C8: `de65834024828db34fa542479fa892e1d14fa764f7d710b95dee595a5899c527`.

F103 сообщает 128 KiB Flash, профиль оставлен 64 KiB; штатное предупреждение,
образ укладывается в обе границы. Это не расширение поддерживаемого диапазона.
GDB/версии backend и индивидуальные отчёты сохранены в result.json каждого запуска.
Сводка 44 аппаратных запусков — `build/elf-regions-validation/summary.json`;
сборочные/host логи там же, подробные HW-артефакты — в профильных hwtest/runs.

## Следующий этап

Отдельно спроектировать полный канонический образ: диапазон, заполнение хвоста
и дырок, действительная запись одинаковых байтов при debug/programming, readback
всего диапазона, параметры CRC и правило поля CRC. Текущий `--gap-fill=0xFF`
при формировании BIN этого режима не реализует. Проверка секций остаётся
самостоятельным режимом, подходящим обычной загрузке ELF через GDB.

Перенос production lifecycle на другие MCU, надзор за процессами и расширение
manifest остаются в дорожной карте отдельного модуля; данный этап не объявляет
общую поддержку RISC-V и не требует возвращения разобранного стенда.
