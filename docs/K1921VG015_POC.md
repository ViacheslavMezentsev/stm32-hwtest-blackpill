# Переносимость на К1921ВГ015: proof-of-concept

2026-09-24. Подтверждённый владельцем стенд: К1921ВГ015, J-Link EDU v11,
полный JTAG. [Пример и команды](../examples/k1921vg015-poc/README.md).
Справочный demo-niiet-cmake/k1921vg015/01-default только читался; изменения,
сборки и журналы находятся в этом репозитории. STM32-стенды не использовались.

## Проверенная конфигурация

- xPack RISC-V GCC 13.3.0-2; rv32imfc_zba_zbb_zbc_zbs_zicsr / ilp32f / -Og -g3.
- GDB 15.1, Python 3.12.2, исполняемый файл riscv-none-elf-gdb-py3.exe.
  Обычный riscv-none-elf-gdb.exe из той же поставки Python не поддерживает.
- J-Link GDB Server 8.32; явный device K1921VG015, JTAG 1000 kHz, Flash BP выключены.
  Сервер обнаружил два JTAG TAP, IRLen=8, JTAG ID 0x00000D5B, RV32/FPU.
- PMUSYS.CHIPID по адресу 0x3000F100 = 0xDEADBEE1; РП v3, стр.300,
  ID[31:4] и REV[3:0]. SVD содержит иное resetValue (0), эталон взят из РП.
- Flash 0x80000000, 1 MiB по разделу 7 РП и linker script; не аппаратная проверка
  всей ёмкости. Таблица карты памяти РП содержит противоречивый верхний адрес,
  поэтому используется более узкая явно описанная граница 0x800FFFFF.
- Vendor startup/system/plic/mtimer и заголовки читаются из внешнего SDK.
  Собственная firmware blink PC0 без RTOS, semihosting и тестовых hooks.

ELF SHA-256:
`c601b1c9351bed71462ccf49e7aa6af61a6941d193a5d75776ccb2d167c5f6ec`.
BIN SHA-256:
`23ab286dd6015e66bd19473069c7be8243a4df4d8b075081cd05de2fccaa06c9`.
Пять загружаемых секций, 3728 байт содержимого, span 3744 байта с промежутком 16 байт.

## Что удалось переиспользовать

Из закреплённого stm32-gdbtest без изменений импортированы Target, CheckFailed,
проверка GDB API, probe_lock и stop_tree. Target boot/reach/value/fields/check
и условные hardware BP работают с RV32/DWARF данного toolchain. Не использовались
production runner/agent, STM32 target schema, identity policy и CMake attach.
В PoC lifecycle явно описан отдельно; результат не означает поддержку К1921
через обычный CLI модуля. Сценарий пока встроен в экспериментальный GDB-агент,
а не в production collection/@case; JUnit/CTest не заявляются.

Регистры RISC-V доступны через GDB; исключения не перехватываются Cortex-M-ловушками.
trap_entry не объявлен аварийной функцией: через него могут проходить штатные IRQ.
Использована одна аппаратная точка одновременно, общий бюджет ещё не измерен.
Строка Type=THUMB в vendor-журнале breakpoint не означает ARM-архитектуру:
сам GDB сообщает riscv:rv32, ELF и выполняемые инструкции RISC-V.

## Выявленное ограничение модели образа

ELF имеет gap 0x80000170..0x8000017F между .text.startup и .text.crt.
objcopy -O binary заполняет его 00; GDB load передаёт только секции,
на плате там прочитано FF. Сравнение сплошного BIN ошибочно объявляло отказ
несмотря на успешную запись реального содержимого.

В PoC список CONTENTS+ALLOC+LOAD строится по objdump, проверяется LMA и диапазон
каждой секции, BSS/stack и gaps не сравниваются. Нельзя просто всегда менять
заполнитель на FF: семантика незагружаемого участка и предыдущие данные различаются.
Это важная задача общего модуля, применимая и к STM32 с разреженным ELF.

## Следующий шаг архитектуры

1. Описать toolchain явно (GDB/objcopy/objdump), убрать предположение arm-none-eabi.
2. Разделить backend и transport/device: J-Link не означает SWD; учесть JTAG chain
   и фактическую доступность vendor device definition в окружении процесса.
3. Вынести identity и memory layout/capacity в адаптер MCU; сведения о границах
   сопровождать источником: register, документация или подтверждённый профиль.
4. Ввести проверку образа по load regions, включая LMA .data и sparse layouts,
   с отрицательными host-тестами до аппаратной записи.
5. Архитектурный адаптер: CSR/диагностика, исключения/IRQ, ABI и допустимые инъекции.
6. После этого повторить PoC через production CLI/@case/CMake/manifest и регрессию STM32.

Копия движка с именем bm310-gdbtest не понадобилась для опыта. Результат поддерживает
идею общего ядра и адаптеров MCU/архитектуры, но ещё не обосновывает универсальную
поддержку RISC-V. force_return, IRQ/DMA, low-power, RAM loading, fault traps,
безопасное завершение после crash host и точные временные/электрические измерения
остаются вне доказанной области. Номинальные 500 мс и SystemCoreClock — программные
ожидания, не измерение внешним эталоном.
